## 1. k6란 무엇이고 왜 하는가

**k6는 가짜 사용자를 대량으로 만들어 서버에 요청을 보내고 응답 시간·오류율을 재는 부하 테스트 도구다.** 우리 프로젝트에 라이브러리로 넣는 것이 아니라 따로 실행하는 프로그램이고, 시험 시나리오를 JavaScript로 쓴다. 서버 코드와 `build.gradle`·`package.json`은 바뀌지 않는다.

**왜 로컬 컨테이너에서 하는가.** 운영 서버(Cloudtype, 메모리 1GB)에 최악 부하를 걸면 실제 이용자와 수집·재계산에 영향을 주고 터지면 장애가 된다. 그래서 같은 조건(메모리 1GiB, 힙 `-Xmx512m`, CPU 1개)의 컨테이너를 PC의 Docker에 만들어 부하를 건다.

**확인하려는 것 (ROADMAP Task 100과 합의 내용)**

| 측정 | 질문 | 사용처 |
|---|---|---|
| 평상시 응답 시간(S1~S4) | 낮은 부하에서 얼마나 빠른가 | 개선 전 기준선, R11-29(응답 시간 목표) 근거 |
| 최악 입력(S5) | 상한 근처 입력에서 계산 시간과 메모리는 | R11-30(상한 유지) 근거 |
| 한계 찾기(S6) | 부하를 올리면 어디서 무엇이 먼저 무너지나 | 병목 위치, 용량 판단 |
| 메모리 | 1GB로 충분한가(1.5GB가 필요한가) | 구독 메모리 판단(512MB당 월 6,600원) |

**이득**: 요금 판단의 근거가 생기고, PRD에서 "측정 후 확정"으로 남겨 둔 수치(R11-29·30)를 숫자로 닫을 수 있고, 트래픽이 몰릴 때 먼저 터지는 곳을 운영 전에 안다. 개선 전후를 같은 조건으로 비교할 수 있는 기준선이 생긴다.

**하지 않은 것**: 512MB 판정(구독 메모리 1GB로 확정이라 의미가 없어 사용자가 제외), CPU 0.5 참고 측정, 수집(Spring Batch) 동시 실행(로컬에서도 TMDB 실호출이 필요).

## 2. k6를 어떻게 쓰는가

### 2-1. 구성 요소와 흐름
1. 시나리오를 `infra/k6/*.js`에 JavaScript로 쓴다(어떤 요청을, 얼마나, 어떤 순서로).
2. 도커 컨테이너로 실행한다. k6 설치가 필요 없다.
   `docker compose -f infra/docker-compose.yml --profile perf run --rm --no-deps k6 run /scripts/<파일>.js`
3. k6 컨테이너가 시나리오를 읽고 가상 사용자를 만들어, 같은 도커 네트워크의 **측정용 백엔드 컨테이너**(`http://backend-perf:8080`)로 HTTP 요청을 보낸다. 운영 서버와 인터넷으로는 나가지 않는다.
4. 끝나면 k6가 응답 시간·오류율·처리량을 요약해 JSON·CSV로 저장한다.

### 2-2. 용어
| 용어 | 뜻 |
|---|---|
| 가상 사용자(VU) | 스크립트의 `default` 함수를 혼자 반복 실행하는 흐름 하나. VU 20이면 사람 20명이 동시에 쓰는 것과 같은 요청 패턴 |
| 반복(iteration) | VU 한 명이 `default` 함수를 한 번 실행하는 것 |
| 대기(`sleep`) | 반복 사이에 쉬는 시간(사람이 화면을 보는 시간) |
| 임계값(thresholds) | "이 기준을 넘으면 실패"라는 합격선. `abortOnFail`이면 넘는 순간 시험을 멈춘다 |
| p95 | 요청의 95%가 이 시간 안에 끝났다는 뜻(중앙값은 p50) |
| 실행기(executor) | 부하를 어떻게 늘릴지 정하는 방식 |

### 2-3. 시나리오 코드의 뼈대 (개념 예시)
```javascript
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  scenarios: {
    stress: { executor: 'ramping-vus',
      stages: [{ duration: '1m', target: 5 }, { duration: '1m', target: 20 }] },   // 단계별 목표 VU 수
  },
  thresholds: {
    http_req_failed: [{ threshold: 'rate<0.01', abortOnFail: true }],   // 오류 1% 초과 시 즉시 중단
    http_req_duration: ['p(95)<1000'],
  },
};

export default function () {                         // VU 한 명이 이 함수를 계속 반복한다
  const res = http.get(`${__ENV.BASE_URL}/api/public/titles?q=...&size=20`);
  check(res, { '200 응답': (r) => r.status === 200 });
  sleep(1);
}
```
공식 문서(Grafana k6, context7 `/websites/grafana_k6`)로 확인한 내용: `ramping-vus`는 단계(stages)마다 목표 VU 수로 선형 증감하고, `thresholds`의 `abortOnFail`은 합격선을 넘는 즉시 중단하며, `setup()`의 반환값은 각 VU에 복사본으로 전달된다.

### 2-4. 사용자를 늘리는 두 가지 방식
| 방식 | 정하는 것 | 서버가 느려지면 | 이 프로젝트에서 |
|---|---|---|---|
| VU 기준(`ramping-vus`) | 동시 사용자 수를 단계별로 | 응답이 길어지면 VU가 오래 기다려 **요청 수도 줄어듦** | 계산 한계 찾기 |
| 도착률 기준(`ramping-arrival-rate`) | 초당 시작할 반복 횟수 | 서버가 느려져도 요청을 계속 보내 **한계가 뚜렷이 드러남** | 읽기·혼합 한계 찾기 |

숫자 예: VU 10, 한 반복이 요청 0.2초 + 대기 1초 = 1.2초면 서버에는 초당 약 8~9건이 들어온다. 서버가 느려져 응답이 2초가 되면 반복이 3초가 되어 초당 약 3.3건으로 줄어든다(VU 기준의 특징).

### 2-5. 로그인(JWT)은 k6가 직접 만든다
`/api/me/**`는 `Authorization: Bearer <JWT>`가 필요하다. 서버에 전용 로그인 API를 만들지 않고, k6가 서버와 같은 키로 직접 서명한다(`lib/auth.js`).
1. 서버의 JWT는 HS256, 클레임 `iss`·`sub`(사용자 번호)·`role`·`iat`·`exp`이고, 키는 `app.jwt.secret`을 **Base64로 디코딩한 바이트**다.
2. k6는 `k6/encoding`의 `b64decode`로 키를 얻고 `k6/crypto`의 `hmac('sha256', …, 'base64rawurl')`로 서명한다.
3. 키는 컴포즈의 `JWT_SECRET`(저장소에 공개된 로컬 개발 전용 키, 운영 키가 아님)에서 읽고 출력하지 않는다.
4. 계산은 사용자별 데이터(찜·설정)가 따로여야 실제와 같아서, 측정용 사용자 50명(번호 1~50)을 두고 VU마다 다른 사용자를 쓴다. 같은 사용자가 동시에 계산하면 초안 행이 경합한다.

## 4. 서버 자원은 어떻게 기록하는가
k6는 **클라이언트 쪽 지표**(응답 시간, 오류율, 처리량)만 잰다. 서버 자원은 따로 기록한다.

| 무엇 | 도구 | 방식 |
|---|---|---|
| 컨테이너 CPU·메모리 | `docker stats` | 측정 직전에 `docker stats --format …`를 파일로 스트리밍(백그라운드)하고 끝나면 멈춘다. 컨테이너 바깥에서 본 값 |
| 메모리 부족 종료 | `docker inspect` | `OOMKilled`, `RestartCount`를 전·후에 확인 |
| 힙·GC·스레드·cgroup | 서버의 관리자 API `/api/admin/system-metrics` | k6의 sampler(`lib/sampler.js`)가 5초마다 ADMIN 토큰으로 호출해 지표로 남김 |
| 서버 로그 | `docker compose logs` | 경고·오류 요약 |

docker 명령은 컴포즈 파일에 담는 내용이 아니라 떠 있는 컨테이너를 들여다보는 별도 명령이다. 컴포즈는 컨테이너를 어떻게 띄울지(메모리·CPU 상한)를 적은 설계도다. 다른 프로그램이 쓴 CPU는 `docker stats`의 컨테이너 CPU%에 포함되지 않지만, 컨테이너가 받을 CPU 시간을 줄여 응답 시간을 늘린다.

## 5. 시나리오와 조건
조건 C1: 메모리 1GiB, CPU 1, `-Xmx512m`(Serial GC가 자동 선택됨), DB 연결 풀 5. 모든 측정이 C1이다. 매 회차 순서: 백엔드 재기동 → `redis-perf` `FLUSHALL` → 워밍업 → 본 측정 + `docker stats` 기록.

| ID | 대상 | 실행기·부하 |
|---|---|---|
| S1 | 검색 `GET /api/public/titles?q=…` | 3 VU, 2분 |
| S2a·S2b | 상세 `GET /api/public/titles/{type}/{id}` 캐시 미스·히트 | 3 VU, 1분씩 |
| S3 | 홈 인기 순위 `GET /api/public/popularity-rankings` | 3 VU, 2분 |
| S4 | 평상시 계산 `POST /api/me/plan-drafts` (캐시 미스·히트) | 2 VU, 3분 |
| S5 | 최악 입력 계산 | 1 VU × 5회, 캐시를 피해 반복 |
| S6-읽기 | 검색 4 : 상세 3 : 인기 3 혼합 | 도착률 10→20→40→80→160→320 req/s, 단계 1분 |
| S6-계산 | 평상시 계산 | VU 1→2→4→8→16→32, 단계 1분 |
| S6-혼합 | 읽기 90% + 계산 10% | 도착률 단계 |

**플랜 계산은 결과가 Redis에 24시간 캐시된다.** 캐시 키(입력 해시)에 사용자 번호가 들어가지 않고, 같은 입력이면 사용자가 달라도 캐시를 맞는다. 엔진 비용을 재려면 반복마다 예산을 조금씩 바꿔 캐시 미스를 강제하고, 캐시 히트는 따로 잰다.

**최악 입력(S5)**: 찜 20개(7개 서비스를 모두 덮음, 쿠팡플레이 단위 1개 포함), 7개 서비스 모두 미구독, 예산 100,000원. 상품 7개가 모두 후보로 남으면 후보 조합이 2⁷의 3제곱 = 2,097,152(그리디 전환 상한과 같다)가 된다.

| 20 | 20.0 | 83.7 | 88 | 15 | 480.9 (543) |
| 40 | 40.0 | 86.0 | 91 | 20 | 496.1 (528) |
| 80 | 80.0 | 107.8 | 132 | 25 | 505.9 (518) |
| 160 | 48.5 | 2,374 | 2,574 | 40 | 532.6 (491) |

**한계 세분 측정(1회)**: 80 → p95 121ms, 100 → 138ms, 120 → 210ms(검색 426ms), **140 → 실제 84.6 req/s, p95 2,902ms(검색 3,350ms), 스레드 203개.** 마지막 안정 단계는 120, 무너진 단계는 140이다.
- 나빠진 순서: 검색 p95만 오른다 → 처리량이 목표를 못 따라가고 밀린 반복(dropped)·VU·스레드가 급증한다 → 오류는 끝까지 0%.
- 그동안 CPU 중앙값은 31~40%(포화 아님), 메모리 여유 491MiB 이상, GC 비중 2.1% 이하, 상세·인기 순위는 p95 2~4ms 그대로였다.
- k6 쪽 한계가 아니라는 근거: 120 단계까지 dropped 0, 무너질 때 VU가 상한 400보다 적음. 단 k6 컨테이너 자체의 CPU는 기록하지 않았다.

**계산 (VU 기준, 평상시 입력·캐시 미스·쉼 없음, 3회 중앙값)**

| VU | 처리량 req/s | p95 | 계산 p95 | CPU 중앙 % | GC 비중 |
|---|---|---|---|---|---|
| 1 | 31.7 | 85.9 | 94 | 91 | 0.6% |
| 2 | 75.9 | 80.0 | 90 | 93 | 1.1% |
| **4** | **96.7(최대)** | 101.6 | 106 | 101 | 1.8% |
| 8 | 95.0 | 185.9 | 200 | 102 | 3.3% |
| 16 | 85.6 | 340.6 | 381 | 102 | 7.9% |
| 32 | 77.6 | 698.1 | 768 | 101 | 9.1% |

처리량은 PUT과 계산을 합친 요청 기준이라 계산은 약 절반이다. 32 VU까지 중단·오류 없음. CPU가 1 VU부터 포화되고, 응답 시간은 VU 수에 비례해 늘고, GC 비중이 오르며 처리량이 4 VU 정점에서 15~25% 줄었다. 메모리는 그대로였다.

**혼합 (읽기 90% + 계산 10%, 1회)**: 80 req/s까지 p95 약 115ms(마지막 안정 단계), 160 단계에서 중단(실제 57 req/s, p95 3,358ms). 읽기만일 때와 달리 CPU 중앙값이 89%까지 오르고 Redis 경로인 인기 순위까지 833ms로 느려졌다(계산이 CPU를 나눠 가져 모든 API가 함께 느려짐).

**최악 입력 동시 계산(1회)**: 동시 1 → p95 4.3초, 2 → 8.6초, 4 → 20.0초. 코어 하나를 나눠 써서 동시 건수에 비례해 늘고 처리량은 계산 약 0.23건/초로 고정된다. GC 비중 8.1 → 13.2%.

## 7. 메모리와 1GB 판단

### 7-1. 이번 부하에서의 메모리
| 측정 | 컨테이너 첫 단계 → 최댓값 (MiB) | 증가 | 1GiB까지 남은 최소 여유 | 힙 used 최대 |
|---|---|---|---|---|
| S6-읽기 | 467~475 → 519~541 | +51~66 | 483 | 153MB |
| S6-계산 | 483~514 → 499~542 | +16~28 | 482 | 156MB |
| S6-혼합 | 476.6 → 580.4 | **+104** | **444** | 142MB |
| 최악 입력 동시 계산 | 462.3 → 476.9 | +15 | 547 | 131MB |

OOM 0건, 재시작 0건. 메모리 압박 신호는 없었다. 동시 계산에서 GC 시간 비중이 10~13%까지 오른 것은 메모리 부족이 아니라 작은 Eden에서 영 GC가 자주 도는 CPU 효율 문제로 본다(추정).

### 7-2. 운영 실측과 합친 추정 (모두 추정)
운영 실측: 수집 뒤 RSS 약 700~742MiB(Max 742MiB), 힙 상한 `-Xmx512m`.

| 가정 | 운영 고원 + 이번 증가분 | 합계 | 1GiB까지 여유 |
|---|---|---|---|
| 계산 위주 부하 | 700~742 + 16~28 | 716~770 | 254~308 |
| 읽기 한계 근처 | 700~742 + 51~66 | 751~808 | 216~273 |
| 혼합 한계 근처 | 700~742 + 104 | 804~846 | 178~220 |

수집으로 늘어난 힙이 이미 고원에 들어 있을 수 있어 로컬 증가분을 그대로 더하면 이중으로 셀 수 있다(위쪽으로 치우친 추정). 이번 측정에는 **수집과 운영의 관측·추적 전송이 없다.** 그래서 1GB를 유지하는 판단에는 추적을 켠 운영 서버의 수집 뒤 메모리를 한 번 더 확인한다.

**결론(사용자 결정 2026-11-03): 1GB 유지.** 이번 데이터로는 1GB 상한에 막힌 신호가 없다.

## 8. 운영에 옮길 때 읽는 법, 한계와 오차
- **절대 수치를 옮기지 않는다.** 운영은 CPU 구독이 없어 기동이 380~414초로 로컬(약 28초)보다 약 14배 느리다(요청 처리에 같은 비율이 적용된다는 근거는 없다). DB(Supabase)는 네트워크 너머라 DB 쿼리가 2개인 검색은 왕복 지연이 더 붙는다. 운영의 공개 API는 IP당 분당 60회로 제한되고 이번 한계 부하(초당 120~140)는 운영에서 그대로 오기 어렵다.
- 가치가 있는 것은 상대적 위치(읽기는 검색이 먼저, 계산은 CPU가 먼저, 메모리는 여유)와 개선 전 기준선이다.
- **PC 간섭**: 22:02~22:18에 다른 프로그램 업데이트로 CPU가 불안정했다. 같은 시나리오 다른 회차 중앙값 대비 med 또는 p95가 +25% 넘게, +2ms 넘게 느린 회차를 의심 회차로 보고 3개 회차(읽기 r3·r4, 계산 미스 r1)를 빼고 다시 쟀다. 원본은 지우지 않았다. S6 3회 편차는 단계별 ±25% 안이었다.
- **알려진 결함·한계**
  1. S6-읽기의 "상세 캐시 미스" 구간은 처음 약 600건 뒤부터 사실상 캐시 히트다(키 선택 결함). 한계 결론(검색이 원인)에는 영향이 없지만 그 구간의 상세 p95를 DB 경로 값으로 읽으면 안 된다. S2a는 문제없다.
  2. 혼합·최악 입력 동시 계산·읽기 세분 측정은 1회씩이라 편차를 모른다.
  3. 검색 병목이 DB 연결 풀(5)인지 PostgreSQL인지는 풀 대기 수·PostgreSQL CPU를 재지 못해 **추정**이다.
  4. 홈 인기 순위는 합성 시드이고 캐시(60분)를 대부분 맞아 DB 경로 시간은 첫 요청(약 190~210ms)뿐이다.
  5. k6의 검색어 30개 중 21개가 1~2글자다(70%). 검색 기준선은 짧은 검색어 위주다(9절).
  6. 서버를 껐다 켤 때마다 배치 reader 4개의 종료 경고(WARN)가 난다. 측정에는 영향이 없고 운영 종료 로그에도 나올 수 있다(고치지 않았다).

## 10. 다시 돌리는 방법 (저장소 루트에서)
```powershell
docker compose -f infra/docker-compose.yml up -d                    # 개발 postgres·redis (이미 떠 있으면 생략)
.\infra\k6\prepare-perf-db.ps1 -Users 50                            # 측정 DB 복사본 생성 (개발 백엔드는 꺼 둔다)
cmd /c "docker compose -f infra/docker-compose.yml exec -T postgres psql -U ottnavi -d ottnavi_perf -v ON_ERROR_STOP=1 -f - < infra\k6\seed-perf-popularity.sql"   # PowerShell은 < 리다이렉트를 못 써서 cmd를 거친다
cd backend; .\gradlew.bat bootJar -x test; cd ..                    # 측정용 jar
docker compose -f infra/docker-compose.yml --profile perf up -d --build --wait backend-perf
docker compose -f infra/docker-compose.yml --profile perf run --rm --no-deps k6 run /scripts/prepare-users.js   # 사용자 설정·찜 입력
bash infra/k6/run-measure.sh read-baseline.js read_C1_r1 440                                                   # S1~S3 한 회
bash infra/k6/run-measure.sh plan.js s5_C1_r1 200 -e MODE=worst -e VARIANT=W3                                  # S5 한 회
K6_CSV=1 bash infra/k6/run-measure.sh stress.js s6read_C1_r1 420 -e MODE=read                                  # 한계 찾기(읽기)
```
`run-measure.sh`가 재기동 → `redis-perf` `FLUSHALL` → 워밍업 → 본 측정 → `docker stats` 기록까지 한다. 결과는 `infra/k6/results/`에 쌓인다. 측정 중에는 PC의 다른 무거운 작업과 프로그램 업데이트를 피한다.
