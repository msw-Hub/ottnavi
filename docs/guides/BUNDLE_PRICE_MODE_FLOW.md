# 번들·저가형 요금제와 "가장 저렴한 요금제로 계산" 모드: 기존 알고리즘과 변경 흐름 (Task 076)

> 사용자가 요청해 만든 설명 문서다. 근거 문서가 아니고 **코드가 기준**이다(규칙의 근거는 PRD·ERD·TECH). 2026-10-17 설계 기준이다. 요금 분류·모드(1단계)와 엔진·입력 조립(2단계)은 구현됐고, 코드와 다른 곳은 아래 "구현 메모"에 적었다. 가격은 모두 설명용 가정이다.
> 한 줄 요약: 서비스마다 계산에 쓸 단품을 1개로 줄이고(모드에 따라 표준 또는 가장 싼 것), 번들을 후보에 더하며, 엔진은 "서비스가 겹치는 상품은 한 달에 1개만"이라는 규칙 하나만 추가한다.

## 1. 확정된 결정 (2026-10-17, 사용자)

| 영역 | 내용 |
|---|---|
| 모드 | 내 설정의 체크 "가장 저렴한 요금제로 계산할래요", 기본 끔 |
| 모드 끔 | 서비스마다 **표준** 단품 중 가장 싼 것. 표준이 없으면 저가형 중 가장 싼 것(서비스가 사라지는 것을 막는 안전장치) |
| 모드 켬 | 서비스마다 **모든 단품 중 적용 금액이 가장 싼 것**(분류와 무관) |
| 번들 | 번들도 표준/저가형 분류를 가진다. 끔=표준 번들만, 켬=모든 번들이 후보 |
| 시청 범위 | 저가형·광고형·베이직은 볼 수 있는 작품에 제한이 없다고 본다(사용자 판단, 시장 사실은 확인하지 못했다). 요금 분류는 **가격 선택에만** 쓴다. `product_component.tier`와 `availability.in_ad_tier`는 수집·저장하되 시청 판정에 읽지 않는다 |
| 겹침 | PRD 11절 33번: 같은 달에 어떤 서비스를 볼 수 있게 하는 상품(단품·번들)은 최대 1개. 결정 1: 이번 달(0번째 달)에 구독 중인 서비스와 겹치는 상품은 후보에서 뺀다(무료 이용 서비스는 제외 근거로 쓰지 않는다) |
| 구독 입력 | 구독 상태는 서비스 단위 그대로. 번들 구독 입력은 만들지 않고 번들은 항상 미구독으로 본다. 번들 이용자는 포함된 서비스를 각각 "구독 중"으로 입력하게 안내한다 |
| 절감액 | 서비스마다 고른 단품 1개 × 3개월(번들 제외)을 "전체 구독 비용"으로 쓴다. 모드를 켜면 가장 싼 단품 기준이다 |
| 번들 등록 | 구성은 등록할 때만 정한다(편집 API 없음, 판매 종료 후 새로 등록). 판매 중 번들은 13개까지 |
| 범위 | 첫 공개 `v0.1.0`에 포함 |

## 2. 기존 알고리즘 흐름

```
사용자 설정(예산, 시청 시간, 구독 상태) + 찜 + 상품 목록
        │
        ▼
[1] PlanInputService.buildProducts
      판매 중 상품마다: 가격 상한(100만 원) 초과면 제외
      구독 상태(FREE/SUBSCRIBED/NONE)를 "그 상품이 속한 서비스"의 상태로 붙임
      → 서비스가 같은 상품은 전부 같은 상태 (넷플릭스 스탠다드·프리미엄 모두 SUBSCRIBED)
        │
        ▼
[2] PlanInputService.buildUnits
      작품마다 "AVAILABLE인 서비스의 모든 상품"을 시청 가능 상품에 넣음
        │
        ▼
[3] 엔진 PlanTypeSolver.solveAll (추천형 → 절약형 → 간편형)
      SolverSelector: 후보 조합 수가 상한(128³ = 2,097,152) 이하면 완전탐색, 넘으면 그리디
        │
        ├─ 후보 제외(S6): FREE / 0번째 달 SUBSCRIBED / 어떤 작품도 못 보는 상품 / 월 예산을 넘는 가격
        ├─ 달별 부분집합(S1·S2): 남은 상품의 모든 부분집합 중 비용 ≤ 월 예산
        │     ★ 같은 서비스 상품 둘이 한 달에 함께 나올 수 있음
        ├─ 동치 제거(S7): 추천형만, 같은 작품 집합을 보는 부분집합은 1등만
        └─ 평가기(Evaluator): 조합마다 작품을 달에 배정 → 꼭 시청 완료 수·점수·비용
              비교기(추천형/절약형/간편형)로 최선 조합 선택
        │
        ▼
[4] 저장·응답
      plan_assignment.ott_service_id = 그 상품의 서비스 1개 (상품 1개 = 서비스 1개라는 가정)
      절감액 = AllSubscribeCostCalculator(시청 가능 상품 합집합 × 3개월) − 플랜 총비용
```

기존에는 번들 개념이 코드에 없고 단품 여러 개를 등록하는 것만 가능했다. 한 서비스에 단품이 둘 이상이면 [1]~[2]에서 전부 후보가 되어 같은 서비스를 한 달에 두 번 고르는 조합이 나올 수 있고, [4]의 전체 구독 비용이 부풀려진다. 상품이 32개를 넘으면 평가기가 예외를 던진다.

## 3. 변경된 알고리즘 흐름

```
사용자 설정(+ 새 모드) + 찜 + 상품 목록(+ 저가형 분류, 번들)
        │
        ▼
[1'] CalcCandidateRules (신규): 서비스마다 단품 1개 + 번들 고르기
      가격 상한(100만 원) 초과는 이 선택 전에 먼저 뺀다(표준 단품이 상한을 넘으면 다음으로 싼 단품이 후보가 된다)
      모드 끔: 표준 단품 중 가장 싼 것 (표준이 없으면 저가형 중 가장 싼 것)
      모드 켬: 그 서비스의 모든 단품 중 적용 금액이 가장 싼 것
      번들: 끔=표준 번들만, 켬=모든 번들
      같은 금액이면 작은 ID, 사용자가 고친 금액 반영
        │
        ▼
[2'] 구독 상태 붙이기
      FREE/SUBSCRIBED는 고른 단품 1개에만, 번들은 항상 미구독(NONE)
        │
        ▼
[3'] buildUnits: 작품의 시청 가능 상품 = AVAILABLE 서비스의 단품 + 그 서비스가 구성에 든 번들
      (요금제 종류와 무관, 시청 범위 제한 없음)
        │
        ▼
[4'] 엔진 (구조는 그대로, 아래만 바뀜)
        ├─ OttProduct에 서비스 목록(ottServiceIds) 추가
        ├─ S6 확장: 0번째 달에 "구독 중 서비스와 겹치는 번들"도 제외
        ├─ S1b 신규: 달별 부분집합에서 서비스가 겹치는 상품 쌍이 함께 든 모양은 버림
        ├─ S7(추천형), 평가기, 비교기 3종, 완전탐색/그리디 선택은 그대로
        └─ 입력 해시 v3(상품 문자열에 서비스 ID 포함)
        │
        ▼
[5'] 저장·응답
      배정 서비스 = (작품이 AVAILABLE인 서비스) ∩ (상품의 구성 서비스) 중 ID가 가장 작은 것
      상품 응답 = ottServiceIds(목록)
      절감액 = 고른 단품 1개씩 × 3개월 − 플랜 총비용 (번들 제외, 모드를 따름)
```

## 4. 구간별 비교

| 구간 | 기존 | 변경 |
|---|---|---|
| 상품 후보 | 판매 중 상품 전부 | 서비스마다 단품 1개 + 번들(모드 규칙) |
| 구독 상태 | 서비스의 모든 상품에 붙임 | 고른 단품 1개에만, 번들은 미구독 |
| 달별 조합(S1·S2) | 예산 이하 부분집합 전부 | 서비스가 겹치는 조합은 버림(S1b) |
| 후보 제외(S6) | FREE, 0번째 달 구독 중, 못 보는 상품, 예산 초과 가격 | 위 + 0번째 달에 구독 중 서비스와 겹치는 번들 |
| 평가기·비교기·탐색 선택 | — | 그대로 |
| 전체 구독 비용 | 시청 가능 상품 합 × 3 | 고른 단품 1개씩 × 3 |
| 배정 서비스 | 상품의 서비스 1개 | 구성 서비스 중 작품이 제공되는 것 중 ID가 가장 작은 것 |
| 상품 응답 | `ottServiceId` | `ottServiceIds`(목록) |

## 5. 같은 입력으로 돌려 보기

월 예산 30,000원. 상품: 넷플릭스 스탠다드 N(13,500), 넷플릭스 광고형 N'(7,000, 저가형), 티빙 T(13,500), 웨이브 W(10,900), 번들 B = 티빙+웨이브(16,000, 표준). 찜한 작품이 티빙과 웨이브에 걸쳐 있고 한 달에 둘 다 필요하다고 가정한다.

| 단계 | 기존 (단품만 등록) | 변경 (모드 끔) |
|---|---|---|
| 후보 상품 | N, N', T, W (넷플릭스 단품 2개 모두) | N, T, W, B (넷플릭스는 가장 싼 표준 1개) |
| 달 부분집합(≤ 30,000) | 단품 4개의 예산 이하 부분집합 전부. {N, N'}(20,500)처럼 같은 넷플릭스를 두 번 고르는 조합 포함 | {}, {N}, {T}, {W}, {B}, {N,T}, {N,W}, {T,W}, {N,B}. S1b로 {T,B}, {W,B}는 버림(예산 안이지만 티빙·웨이브가 겹침) |
| 티빙·웨이브 둘 다 필요한 달 | {T,W} = 24,400원 | {B} = 16,000원이 더 싸서 추천형·절약형이 선택, 간편형은 가입 횟수가 적은 번들 선택 |
| 전체 구독 비용 | N, N', T, W 합 × 3 = 44,900 × 3 | 고른 단품 N, T, W 합 × 3 = 37,900 × 3 |
| 배정 서비스 | 상품 1개 = 서비스 1개 | 번들 B면 작품이 티빙에서만 제공되면 티빙, 둘 다면 ID가 작은 티빙 |

모드를 켜면 N 자리에 N'(7,000, 가장 싼 단품)가 들어간다. 티빙·웨이브는 더 싼 단품이 없으면 그대로 쓴다. 번들은 모든 번들이 후보다.

## 7. 알려진 한계

1. **번들 이용자**: 구독 상태가 서비스 단위라 번들 이용자는 포함된 서비스를 각각 "구독 중"으로 입력한다. 이번 달은 정확하다. 다음 두 달은 비용은 맞지만 안내가 "번들 가입"으로 나오고, 간편형은 번들을 새 가입 1회로 세어 단품 둘을 골라 월 8,400원(가정)가량 많게 보인다. 공개 뒤에 사용자가 이용 중인 상품을 직접 고르게 하는 기능으로 개선한다.
2. **모드와 실제 요금제 불일치**: 모드를 끄고 실제로는 저가형을 쓰면 이어 구독 비용이 표준 가격으로 계산된다. 켜고 실제로는 표준을 쓰면 요금제를 낮추는 것으로 본다.
3. **모드를 바꿔도 저장된 ACTIVE 플랜은 그대로**다. 다음 계산(재계산 포함)부터 반영하고 설정 화면에 안내 문구를 둔다. 모드 때문에 상품이 바뀌어도 변경 내역 이유 4종에 해당하지 않으면 변경 내역에 기록되지 않는다.
4. **후보 수**: 번들 3개 + 단품 7개이면 달마다 후보가 최대 208개로, 예산이 큰 사용자의 절약형·간편형은 그리디로 바뀌는 경우가 생긴다. 추천형은 S7로 줄어든다. 실측은 Task 100.
5. **배정 서비스 표시는 임의 규칙**이다. 같은 번들에서 작품이 한 서비스에서 빠지고 다른 서비스에만 남으면 배정 서비스가 바뀌어 변경 내역에 서비스 바뀜으로 기록될 수 있다.
6. 시장 사실(요금제 종류, 가격, 번들 구성, 광고형이 실제로 작품을 제한하는지)은 확인하지 못했다.

## 8. 구현 메모 (2단계, 코드 기준)

| 항목 | 설계 문서 내용 | 구현 |
|---|---|---|
| S6 확장의 달 범위 | 0번째 달에 구독 중 서비스와 겹치는 번들 제외 | **0번째 달 후보에서만** 뺀다. 1·2번째 달에는 번들이 후보로 남고, 구독 중 단품과 같은 달에 못 고르는 것은 S1b가 맡는다. 무료 이용(FREE) 서비스는 근거가 아니다 |
| 가격 상한 제외 순서 | [1']에서 후보 선택과 함께 | 상한 초과 상품을 `CalcCandidateRules.select`에 넣기 전에 먼저 제외한다(`PlanInputServiceBundleTest`가 순서를 고정). 상한을 넘은 상품 ID는 `excludedProductIds`에 남는다 |
| `OttProduct` | `ottServiceIds` 추가 | 4번째 인자로 추가하고 오름차순 불변 목록으로 보관한다. 3개 인자 생성자(서비스 정보 없음, 겹침 검사 대상 아님)는 테스트·벤치마크 호환용으로 남겼다. `isBundle()`은 구성 서비스 2개 이상이다 |
| 입력 해시 | v3, 상품 문자열에 서비스 ID | `id:가격:구독 상태:서비스ID(오름차순, 쉼표)` 형식이고 서비스 정보가 없으면 `-`다 |
