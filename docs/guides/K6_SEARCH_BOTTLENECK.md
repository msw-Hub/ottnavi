# k6로 찾은 검색 병목과 개선 과정

> 설명·기록 문서이고 근거 문서가 아니다. 측정 방법과 전체 결과는 `K6_PERFORMANCE.md`에 있고, 이 문서는 그중 **검색 문제 하나를 끝까지 따라가는 이야기**다.
> 진행 상태(2026-11-03): 문제 확인 → 원인 분석 → 인덱스 실험 → **같은 날 세 구성(인덱스 없음 / 인덱스만 / 인덱스 + 매번 계획 세우기) 측정**까지 끝났다. 인덱스만 넣으면 2글자 검색이 오히려 느려지고(4-6), 매번 계획 세우기를 더하면 해결된다는 것을 측정으로 확인했다(7장). **"매번 계획 세우기"는 설정 파일 한 줄(5-6)로, 1글자 검색 제한(8장)은 계약·백엔드·프론트에 걸쳐 이번 개선 PR에서 구현했다.** 운영 배포 뒤 다른 쿼리의 응답 시간 확인이 남아 있다(5-5).

## 1. 한눈에 보기

운영과 같은 조건(메모리 1GiB, CPU 1개)의 로컬 컨테이너에 k6로 부하를 걸었더니, 읽기 API 중 **검색이 가장 먼저 무너졌다.** 원인을 찾아 인덱스를 넣었고, 그 과정에서 인덱스만으로는 부족하다는 것을 알게 되어 설정을 하나 더했다.

| 단계 | 내용 | 핵심 숫자 |
|---|---|---|
| 1. 발견 | 초당 요청을 올리는 시험에서 140건 단계에 응답 시간이 급증(2026-11-02) | p95 210ms(120건) → 2,902ms(140건) |
| 2. 원인 추적 | 그때 CPU는 30%대, 느려진 것은 검색뿐 | 검색 p95 426ms → 3,350ms, 상세·인기 순위는 2~4ms 유지 |
| 3. 가설 확인 | 검색이 작품 33,004건을 두 번 순서대로 읽음 | `EXPLAIN ANALYZE`: 순차 스캔 49ms + 32ms |
| 4. 해결책 실험 | 트라이그램 인덱스를 측정 DB에서 시험 | 3글자 한글 32.9ms → **0.14ms**, 2글자 한글은 변화 없음 |
| 5. 인덱스만 적용(C1) | 같은 날 A/B로 측정 | 3글자 이상 68.7 → **9.6ms**, 그러나 2글자 이하 67.7 → **119.9ms(느려짐)**, 읽기 한계는 그대로 |
| 6. 원인 규명 | DB가 같은 쿼리를 반복하면 계획을 하나로 굳히는데, 2글자에서는 그 계획의 견적이 틀림 | 견적 1,025(색인) vs 4,059(훑기), 실제 59ms vs 30ms |
| 7. 매번 계획 세우기 추가(C2) | 연결마다 `plan_cache_mode = force_custom_plan` | 2글자 이하 **65.5ms**(처음 수준), 3글자 이상 **10.3ms**, 읽기 마지막 안정 단계 **160 → 275 req/s** |

## 2. 문제를 발견하기까지

### 2-1. 무엇을 쟀나
k6는 가짜 사용자를 대량으로 만들어 서버에 요청을 보내는 도구다. 운영과 같은 조건의 측정용 컨테이너(복사한 DB 포함)에 다음을 걸었다.

1. 평소 속도: 검색 73ms, 상세 2~7ms, 홈 인기 순위 2ms, 평상시 계산 약 40ms.
2. 최악 입력 계산: 3.7초(CPU 1코어를 혼자 사용).
3. **한계 찾기**: 읽기 요청(검색 4 : 상세 3 : 인기 순위 3)을 초당 10건부터 단계적으로 올리고, 오류가 1%를 넘거나 응답 시간(p95)이 1초를 넘으면 자동으로 멈추게 했다.

### 2-2. 한계 찾기에서 일어난 일 (2026-11-02 측정)
같은 시험을 3회 반복했고 3회 모두 **초당 160건 단계에서 멈췄다.** 멈춘 단계 주변을 더 잘게 나눠 다시 쟀다(1회).

| 목표 req/s | 실제 req/s | 응답 p95 | 검색 p95 | 밀린 반복(dropped) | 스레드 | CPU 중앙값 |
|---|---|---|---|---|---|---|
| 80 | 80.0 | 121ms | 141ms | 0 | 35 | 74% |
| 100 | 99.9 | 138ms | 202ms | 0 | 37 | 32% |
| 120 | 120.0 | 210ms | 426ms | 0 | 50 | 31% |
| **140** | **84.6** | **2,902ms** | **3,350ms** | 149 | **203** | 33% |

**마지막으로 안정했던 단계는 120건, 무너진 단계는 140건**이다. 순서는 이렇다.
1. 검색 응답 시간만 먼저 오른다(80건에서 141ms → 120건에서 426ms).
2. 140건에서 처리량이 목표(140)를 못 따라가 84.6건에 머물고, 밀린 반복이 149건 생기며, 요청을 처리하는 스레드가 35개에서 203개로 쌓인다.
3. 오류는 끝까지 0%였다(느려지기만 했다).

> 이 숫자는 **이 발견 시점의 값**이다. 개선 전후 비교(7장)는 같은 날 같은 스크립트로 다시 잰 개선 전 값(마지막 안정 160, 무너짐 180)을 기준으로 한다. 두 값이 다른 이유는 확인하지 못했다. 사이에 서버·DB 컨테이너가 다시 시작됐고 검색어 구성이 바뀐 것(스트레스 스크립트가 30개 중 12개만 쓰던 선택 오류도 이때 고쳤다)이 겹쳐 있다. 이 문서의 개선 효과는 **같은 날 A/B 값만** 근거로 쓴다.

### 2-3. 이 숫자가 알려 주는 것
| 관찰 | 의미 |
|---|---|
| 무너지는 순간에도 CPU 중앙값이 30%대 | 서버가 계산에 지친 것이 아니다. CPU가 원인이 아니라는 신호 |
| 같은 시점에 상세·인기 순위(Redis 캐시 경로)는 p95 2~4ms 그대로 | 서버 전체가 느려진 것이 아니라 **검색 경로만** 막혔다 |
| 스레드가 200개 이상 쌓임 | 요청들이 무언가를 기다리며 줄 서 있다 |
| 메모리 여유 491MiB 이상, GC 비중 2.1% 이하 | 메모리·GC 문제가 아니다 |

그래서 "검색이 쓰는 데이터베이스 경로 어딘가가 막힌다"는 가설을 세웠다.

## 3. 원인을 좁히기

### 3-1. 코드에서 본 것
검색은 제목·원제에 검색어가 **들어 있는** 작품을 찾는다(`TitleRepository.searchByTitle`).
```sql
-- 목록 쿼리 (한 페이지)
select * from title
where title ilike '%검색어%' or original_title ilike '%검색어%'
order by (개봉 시기 그룹), popularity desc ...
-- 개수 쿼리 (전체 건수)
select count(*) from title
where title ilike '%검색어%' or original_title ilike '%검색어%'
```
검색어 **앞에도 `%`가 붙어서**(중간 일치) 일반 인덱스(B-tree)로는 찾을 수 없고, `title` 표에는 기본키와 `(media_type, tmdb_id)` 인덱스뿐이다. 그리고 한 번의 검색 요청이 이 조건의 쿼리를 **두 번** 보낸다(목록, 개수).

### 3-2. 실제 실행 계획으로 확인
측정 DB에서 `EXPLAIN ANALYZE`를 돌렸다.

| 쿼리 | 실행 방식 | 걸린 시간 |
|---|---|---|
| 목록 쿼리 | `Seq Scan on title`(전체 순서대로 읽음, 32,364행을 걸러냄) | 49ms |
| 개수 쿼리 | `Seq Scan on title` | 32ms |

검색 한 번에 작품 33,004건을 **두 번 처음부터 끝까지** 읽는다. 동시에 요청이 몰리면 이 두 쿼리가 DB 연결(최대 5개)을 오래 붙잡고, 나머지 요청은 줄을 서서 스레드가 쌓인다. (여기까지는 지표와 실행 계획으로 **확인한 것**이다. "연결 5개가 모자라서 줄을 선다"는 설명은 풀 대기 수를 재지 않아서 **추정**이다.)

## 4. 해결책 고르기와 실험

### 4-1. 어떤 인덱스인가
앞뒤에 `%`가 붙은 검색은 **트라이그램(trigram) 인덱스**가 다룬다. 글자를 세 글자씩 겹쳐 쪼개서 인덱스에 담는다.
```
'기생충' → 기생충 (3글자라 조각 1개)   'avengers' → ave, ven, eng, nge, ger, ers ...
```
검색어도 같은 조각으로 쪼개 "이 조각들을 모두 가진 작품"을 인덱스에서 바로 찾는다. PostgreSQL의 `pg_trgm` 확장이 제공하고(`gin_trgm_ops`), **쿼리를 바꾸지 않아도** 같은 `ilike '%…%'`가 인덱스를 탄다. 인덱스는 마이그레이션이 실행될 때 **미리 한 번 만들어 두는 것**이고, 검색할 때마다 만드는 작업은 없다.

### 4-2. 실험 방법
측정 DB에서 **트랜잭션 안에 인덱스를 만들고 계획을 본 뒤 되돌렸다.** 측정 DB에는 아무 흔적도 남지 않았다(확인: 인덱스 목록이 실험 전과 같음).

### 4-3. 결과 (개수 쿼리 기준)
| 검색어 | 인덱스 없음 | 인덱스 있음 | 계획 |
|---|---|---|---|
| 3글자 한글 `기생충` | 32.9ms | **0.14ms** | 인덱스 사용(Bitmap Index Scan) |
| 영문 긴 단어 `avengers` | - | 0.21ms | 인덱스 사용 |
| 영문 `the`(결과 3,824건) | - | 5.6ms | 인덱스 사용(결과가 많아 느림) |
| **2글자 한글 `사랑`** | 30.7ms | **31.2ms** | **순차 스캔 그대로(인덱스를 못 씀)** |

- 인덱스 크기: 제목 5.6MB + 원제 6.1MB(표 28MB), 생성 시간 합쳐서 약 0.5초.
- 한글도 조각이 만들어지는 것을 확인했다(`기생충` → 조각 4개).

### 4-4. 2글자가 안 되는 이유
트라이그램은 **세 글자 조각**이라서 검색어가 두 글자 이하면 쪼갤 조각이 없다. PostgreSQL 공식 문서도 "추출할 트라이그램이 없는 패턴은 인덱스 전체를 읽는 것으로 퇴화한다"고 설명한다(`pg_trgm`). 작품 제목 중 2글자 이하가 1,545건(4.7%)이고, 한국어 검색은 2글자가 흔해서 **실제 효과는 사용자가 3글자 이상을 얼마나 검색하느냐**에 달려 있다. 검색어 분포는 개인정보 때문에 로그에 남기지 않아서 알 수 없다.

### 4-5. 앱이 보내는 쿼리 모양으로 다시 확인
위 실험은 `ilike '%검색어%'`를 직접 쓴 쿼리였다. 실제 앱은 검색어를 **바인딩 변수**(`ilike :pattern escape :escapeChar`)로 보낸다. 같은 모양으로 `PREPARE`/`EXECUTE`를 해 본 결과, 3글자 이상은 기본 설정과 일반 계획 강제 모두에서 인덱스를 탔다(목록·개수 쿼리 0.07~0.25ms). 쿼리를 바꾸지 않아도 되는 것을 확인했다. 그런데 이 실험에서 2글자 검색이 **일반 계획으로 바뀌면 인덱스 없을 때(32.9ms)보다 약 2.2배 느려지는(72ms)** 현상이 처음 나타났다. 같은 연결에서 2글자 검색만 5번 이상 이어지면 발생했고, 3글자 이상이 먼저 5번 이상 있으면 2글자도 값 기준 계획(순차 스캔 33ms)을 유지했다. 이 현상은 4-6에서 풀어 쓴다.

### 4-6. 인덱스만 넣으면 2글자 검색이 느려지는 이유 (실행 계획 캐시)

**증상.** 인덱스만 적용한 구성(C1, 7장)에서 3글자 이상은 68.7ms → 9.6ms로 빨라졌지만, 2글자 이하는 67.7ms → 119.9ms로 **오히려 느려졌다.**

**DB가 쿼리를 실행하는 방법을 정하는 방식.** 같은 결과를 내는 방법은 여러 가지다(표를 처음부터 훑기, 인덱스로 찾기 등). PostgreSQL은 방법마다 **실행해 보지 않고 "견적"(비용 숫자)을 계산해서** 가장 낮은 것을 고른다. 견적은 표의 통계(행 수, 값의 분포 등)로 낸다. 실제로 두 방법을 모두 돌려 재는 것이 아니다.

**계획 캐시 규칙.** 검색어를 바인딩 변수로 보내는 쿼리는 "준비된 문장"으로 등록되고, 계획을 두 가지 방식으로 만들 수 있다(PostgreSQL 공식 문서, `PREPARE`).

| 계획 | 만드는 방법 | 특징 |
|---|---|---|
| 사용자 정의 계획(custom plan) | **그 실행의 검색어 값**을 보고 매번 새로 만든다 | 값에 맞는 방법을 고르지만 매번 계획 시간이 든다 |
| 범용 계획(generic plan) | 검색어 값을 **모르는 상태**로 한 번 만들어 재사용한다 | 계획 시간을 아끼지만, 값에 따라 알맞은 방법이 다르면 비효율적일 수 있다 |

기본 설정(`plan_cache_mode = auto`)에서는 **처음 5번은 사용자 정의 계획**으로 실행하고 그 견적의 평균을 구한다. 그다음 범용 계획을 만들어 그 견적을 평균과 비교하고, **범용 계획의 견적이 평균보다 크게 높지 않으면 이후 실행은 범용 계획으로 굳힌다.** 이 판단은 연결(커넥션)마다 따로 일어난다. 이 서비스는 DB 연결이 5개라 연결마다 굳혀진다. (JDBC 드라이버도 같은 문장을 5번 보낸 뒤부터 서버 준비 문장으로 등록하는 기본값이 있다. 이 드라이버 동작은 일반 지식이고 이번에 따로 확인하지 않았다.) 중요한 점은 비교 기준이 **실제 실행 시간이 아니라 견적**이라는 것이다.

**견적이 틀린 사례(C1 측정 중 직접 확인, 개수 쿼리 기준, 읽기 전용 트랜잭션 안에서 계획만 비교).**

| 검색어 | 계획 | 견적(비용) | 선택된 방법 | 실제 시간 |
|---|---|---|---|---|
| 사랑(2글자) | 사용자 정의 | 4,059 | 순차 스캔(훑기) | **30ms** |
| 사랑(2글자) | 범용 | **1,025** | 두 인덱스를 전부 읽음 | **59ms** |
| 크리스마스 | 사용자 정의 | 1,778 | 인덱스 | 0.57ms |
| 크리스마스 | 범용 | 낮음 | 인덱스 | 0.45ms |

- 범용 계획은 검색어를 모르는 상태에서 "인덱스를 쓰면 싸겠다"고 **낙관적으로 견적**을 낸다. 그래서 견적만 보면 범용(1,025)이 사용자 정의(4,059)보다 훨씬 싸 보이고, DB는 범용 계획으로 굳힌다.
- 그런데 "사랑"은 2글자라 쪼갤 3글자 조각이 없다(4-4). 인덱스로 후보를 줄이지 못해 **모든 행(33,004)을 후보로 보고**, 인덱스를 전부 읽고(Bitmap Index Scan) 이어서 표의 모든 행을 꺼내 정말 포함하는지 다시 확인하며(Bitmap Heap Scan, 재검사) 32,364행을 버렸다. **하는 일은 "인덱스 전체 읽기 + 표 전체 확인"이라, 훑기(표를 한 번 읽으며 바로 확인)에 인덱스 읽기가 더 붙은 꼴이다.** 그래서 실제로는 약 2배(59ms 대 30ms) 느렸다.
- 3글자 이상은 범용 계획으로 굳어져도 인덱스 경로가 맞아서 문제가 없다(0.45ms).
- 결국 **DB는 견적이 낮은 쪽을 골랐지만, 견적이 2글자에서 현실과 달랐다.** PostgreSQL 공식 문서도 이 상황(범용 계획의 견적이 크게 어긋나는 경우)에 계획 방식을 강제하는 설정을 쓰도록 안내한다.

**숫자를 읽을 때 단위를 구분한다.** 위 표의 30ms·59ms는 **쿼리 하나(개수 쿼리)가 DB 안에서 실행되는 시간**이고, 앞서 본 67.7ms → 119.9ms는 **검색 요청 한 건 전체의 응답 시간**이다. 한 요청이 목록 쿼리와 개수 쿼리를 모두 보내고 각각 약 2배 느려지므로 요청 전체는 약 1.8배가 된다(쿼리당 약 +29ms씩 합쳐 +58ms로 계산했고, 실제 +52ms와 맞았다).

**C0도 기본 설정(`auto`)이었는데 문제가 없던 이유.** C0에는 인덱스가 없어 **선택지가 순차 스캔 하나뿐**이었다. 굳은 범용 계획도 같은 순차 스캔이라 잘못 고를 일이 없었다. 인덱스가 생겨 선택지가 둘이 되자 굳은 계획이 잘못된 쪽을 고를 수 있게 됐다.

**언제 전환되는가.** 에이전트가 시계열을 봤을 때 2글자 연속 구간(S1b) 중간에 전환 시점이 보이지 않았고, 평상시 측정(S1)의 첫 2글자 요청부터 이미 느렸다. 워밍업과 S1 초반 요청으로 연결마다 5회 기준이 채워져 측정 이전에 이미 전환된 것으로 **추정**한다. 연결별 전환 순간은 재지 않았다.

### 4-7. 매번 계획 세우기(C2)이 하는 일
`plan_cache_mode = force_custom_plan`은 "굳히지 말고 **매번 검색어를 보고 계획을 새로 만들라**"는 설정이다.

- 검색어 값을 알고 견적을 내므로 견적이 정확해진다. "사랑"은 훑기를, "크리스마스"는 인덱스를 **매번** 고른다.
- C2가 새로운 빠른 방법을 찾은 것이 아니다. **C1에서 잘못 굳어진 계획을 피한 것**이다.
- 대가는 매번 계획을 세우는 시간이다. 이번 측정에서 평상시와 한계 부하 모두 응답 시간에 드러나는 차이가 없었다(7장).
- 이 설정은 연결에 걸리므로 쿼리와 자바 코드는 바뀌지 않는다. 반영 방식은 5-6에서 다룬다.
- 이름에 주의한다. 설정 값은 `force_custom_plan`이고 뜻은 "계획을 굳히지 않고 **매번 새로 세운다**"이다. 계획을 고정(재사용)하는 쪽은 오히려 범용 계획이고, 이 문서는 이 설정을 "매번 계획 세우기"라고 부른다.

**글자 수별로 정리하면** 다음과 같다.

| 검색어 | 인덱스(트라이그램)가 하는 일 | 매번 계획 세우기 구성(C2) 결과 | 개선 전(C0) 대비 |
|---|---|---|---|
| 1글자 | 검색을 제한한다(8장) | 해당 없음 | 검색 비용이 사라짐 |
| 2글자 | 3글자 조각이 없어 도움이 되지 않는다. 표를 훑어서 찾는다 | 평균 65.5ms | 거의 같음(67.7ms). 개선이 아니라 **인덱스로 인한 악화를 막은 것** |
| 3글자 이상 | 조각으로 후보를 바로 좁힌다 | 평균 10.3ms | 약 85% 빨라짐(68.7ms) |

**세 구성에서 2글자 검색이 하는 일**

| 구성 | 2글자 때의 계획 | 요청 전체 시간 |
|---|---|---|
| C0 (인덱스 없음, `auto`) | 선택지가 훑기뿐이라 훑기 | 67.7ms |
| C1 (인덱스만, `auto`) | 굳은 범용 계획이 **인덱스 경로**(인덱스 전체 읽기 + 표 전체 확인)를 고름 | 119.9ms |
| C2 (인덱스 + 매번 계획 세우기) | 매번 검색어를 보고 **훑기**를 고름 | 65.5ms |

### 5-1. 마이그레이션 (Flyway V12, 저장소 파일이고 배포 때 자동 실행된다)
`backend/src/main/resources/db/migration/V12__add_title_trgm_search_index.sql`
```sql
CREATE SCHEMA IF NOT EXISTS extensions;                          -- Supabase에는 이미 있어서 아무 일도 안 함, 로컬·테스트 DB에는 새로 만듦
CREATE EXTENSION IF NOT EXISTS pg_trgm WITH SCHEMA extensions;   -- 확장을 설치할 폴더를 명시
CREATE INDEX idx_title_title_trgm ON title USING gin (title extensions.gin_trgm_ops);
CREATE INDEX idx_title_original_title_trgm ON title USING gin (original_title extensions.gin_trgm_ops);
```
**이 문장들을 웹(Supabase 화면)에서 직접 실행하는 것이 아니다.** 마이그레이션 파일에 담겨 배포될 때 서버가 시작하면서 Flyway가 실행한다. 쿼리와 자바 코드는 바뀌지 않는다.

**로컬 검증(2026-11-03).**
1. 빈 임시 DB(`extensions` 스키마 없음)에서 파일을 실행해 스키마·확장·인덱스 2개가 만들어지는 것을 확인했다(임시 DB는 삭제).
2. Testcontainers PostgreSQL에서 Flyway가 12단계를 적용하고 엔티티 매핑 검증이 통과했다(`EntityMappingValidateTest` 1개, 전체 테스트는 PR의 CI가 돈다).
3. 측정 DB에 V12가 든 jar로 서버를 띄워 적용했다(Flyway 12, 인덱스 5.6MB·6.1MB).

### 5-2. "검색 경로에 extensions가 있다"는 말의 뜻
위 `extensions.` 표기와 이어지는 개념이라 풀어 둔다.

| 용어 | 쉬운 뜻 |
|---|---|
| 스키마(schema) | DB 안의 폴더. 테이블·함수 등이 폴더별로 들어 있다(`public`, `extensions` 등) |
| 검색 경로(`search_path`) | 이름만 썼을 때 DB가 **어떤 폴더를 어떤 순서로 찾는지** 정한 목록. Supabase의 현재 값은 `"$user", public, extensions` |
| 확장(extension) | DB에 기능을 더하는 부품. `pg_trgm`은 세 글자 조각 검색 기능을 준다 |
| 연산자 클래스 | 인덱스가 데이터를 **어떤 규칙으로 쪼개 담을지** 정한 부품. `gin_trgm_ops`는 "세 글자 조각으로 GIN 인덱스에 담는 규칙"이고 확장을 설치할 때 생긴다 |

인덱스를 만들 때 `gin_trgm_ops`를 **이름만** 쓰면 DB가 검색 경로의 폴더를 차례로 뒤져 찾고, 어디에도 없으면 `operator class "gin_trgm_ops" does not exist` 오류로 마이그레이션이 실패한다(서버 기동 실패로 이어진다). 그래서 확장을 어느 폴더에 설치하는지가 중요하고, 마이그레이션은 설치 폴더(`extensions`)와 사용 위치(`extensions.gin_trgm_ops`)를 **둘 다 명시**해서 Supabase와 폴더가 없는 로컬·테스트 DB 양쪽에서 같은 파일이 동작하게 했다.

### 5-3. 운영 DB(Supabase)의 현재 상태 (2026-11-03 확인)
| 확인 | 결과 |
|---|---|
| `pg_trgm` 사용 가능 여부 | 사용 가능(기본 버전 1.6) |
| 설치 여부 | 처음 확인했을 때는 **설치 전**(설치된 버전 없음, 어느 폴더에도 없음). 이후 사용자가 5-4의 한 문장을 실행해 설치했고 설치 폴더가 `extensions`로 확인됐다(2026-11-03) |
| 검색 경로 | `"$user", public, extensions` |

### 5-4. 사전 준비(선택, 운영 DB에서 하는 유일한 수동 작업)
앱이 접속하는 DB 계정에 확장 **설치 권한**이 있는지는 확인하지 못했다(Supabase의 기본 `postgres` 계정은 보통 가능). 안전하게 가려면 개선을 배포하기 **전에** Supabase SQL Editor에서 **다음 한 문장만** 실행해 확장을 미리 설치해 둔다. (이번에는 이미 실행해 설치된 상태다.)
```sql
create extension if not exists pg_trgm with schema extensions;
```
- 인덱스 생성문은 실행하지 않는다(배포 때 마이그레이션이 한다).
- 확장 설치는 테이블·데이터를 바꾸지 않고, 인덱스가 만들어지기 전에는 `drop extension pg_trgm;`으로 되돌릴 수 있다.
- 미리 설치해 두면 마이그레이션의 `CREATE EXTENSION IF NOT EXISTS`는 건너뛰므로 권한 문제로 기동이 실패할 위험이 사라진다.

### 5-5. 위험과 확인 목록
| 위험 | 대응 |
|---|---|
| 확장 설치 권한 부족으로 마이그레이션 실패 → 서버 기동 실패 | 5-4의 사전 설치(완료) |
| 로컬·CI(Testcontainers)에서 `extensions` 폴더가 없음 | 마이그레이션의 `CREATE SCHEMA IF NOT EXISTS`와 폴더 명시, 5-1의 빈 DB 검증 |
| 수집 때 `title`을 쓰면 인덱스도 갱신해야 함 | 수집은 하루 수 번, 3만 3천 행 규모라 영향이 작을 것으로 예상(측정하지 않음) |
| 인덱스 생성 중 `title` 쓰기가 잠깐 막힘 | 생성 약 0.5초(측정 DB 기준), 33,192건 규모라 사실상 무시 가능 |
| 매번 계획 세우기가 다른 쿼리의 계획 시간을 늘림 | 이번 측정에서 상세·인기·계산 API는 변화가 없었지만 **평상시 부하에서만 확인**했다. 운영 배포 뒤 응답 시간을 확인한다 |

### 5-6. "매번 계획 세우기"의 반영 방식 (구현 완료)
측정한 구성(C2)과 같게, **연결이 만들어질 때마다 실행되는 초기화 SQL**(Hikari `connection-init-sql`)로 `SET plan_cache_mode = force_custom_plan`을 건다. `application.yml`(공통 설정)에 한 줄을 더했고 쿼리와 자바 코드는 바뀌지 않는다.
```yaml
spring:
  datasource:
    hikari:
      connection-init-sql: SET plan_cache_mode = force_custom_plan
```
- 공통 설정에 둔 이유: 로컬·테스트·운영이 같은 동작을 해야 측정한 구성과 어긋나지 않는다.
- 선택하지 않은 방법: 검색 서비스에서만 트랜잭션 단위로 같은 설정을 거는 방법은 다른 쿼리에 영향이 없지만, 서비스 코드 수정이 필요하고 측정하지 않은 방식이라 쓰지 않았다. 운영에서 다른 쿼리에 문제가 보이면 이 방법으로 범위를 좁힌다.
- 확인한 것(2026-11-03): 설정 파일만으로 반영된 jar를 측정 서버에 띄워(환경 변수 없이) 2글자 검색이 개선 전 수준으로 응답했고, Testcontainers PostgreSQL에서도 Flyway 12단계와 엔티티 매핑 검증이 통과했다.
- 이 설정은 **연결 하나에 거는 설정**이라 운영이 쓰는 Supabase Session Pooler(포트 5432)에서는 연결이 유지되는 동안 유지된다. Transaction Pooler(6543)처럼 트랜잭션마다 다른 DB 연결을 받는 방식으로 바꾸면 설정이 유지되지 않을 수 있어 그때 다시 확인해야 한다(Supabase 일반 동작이며 이번에 따로 시험하지 않았다).

## 6. 개선 전후를 어떻게 비교했나

기존 측정에는 **검색어 글자 수 구분이 없었고**, 검색어 30개 중 21개(70%)가 1~2글자였다. 그대로 비교하면 3글자 이상의 개선 폭이 묻힌다. 그래서 다음처럼 했다.

1. **검색어를 글자 수별로 균형 있게 구성**했다(2글자 이하 15개, 3글자 이상 15개, 모두 DB에 결과가 20건 이상). 요청마다 글자 수 태그(`short`: 2글자 이하, `long`: 3글자 이상)를 달아 결과를 분리해서 보고한다. 3글자 이상에는 결과가 1,000건을 넘는 영문 2개(`the` 3,824건, `ing` 1,154건)가 들어 있는데, 한글 3글자 이상 검색어 중에는 1,000건 넘는 것이 후보에 없어서다.
2. **같은 날 A/B/C**: 세 구성을 같은 조건(1GiB, CPU 1, `-Xmx512m`, 같은 데이터, 같은 스크립트)으로 연달아 쟀다.

| 구성 | 내용 | 만든 방법 |
|---|---|---|
| C0 | 인덱스 없음(개선 전) | V11 상태의 `backend-perf` 이미지 그대로 |
| C1 | 인덱스만 | V12가 든 jar로 `backend-perf`를 다시 빌드·재생성 |
| C2 | 인덱스 + 매번 계획 세우기 | C1과 같은 jar에 compose 파일을 얹어 환경 변수(`SPRING_APPLICATION_JSON`의 `connection-init-sql`)만 추가 |

3. **구성마다 같은 순서**: 재기동 → 측정 전용 Redis 비우기 → 워밍업 → 평상시 검색 3회(중앙값) → 읽기 한계(100~140, 140~200 두 범위를 1회씩, 붕괴가 없으면 더 높은 범위 추가).
4. **2글자 연속 구간(S1b)**: 같은 연결에서 같은 문장이 반복될 때만 생기는 계획 전환을 드러내려고 2글자 검색만 이어 보내는 구간을 추가했다(5명, 2분, DB 연결 풀 5개와 같은 수).
5. 비교 항목: 평상시 검색 응답 시간(글자 수별), 읽기 한계(마지막 안정 단계, 무너진 단계), 무너질 때 검색 p95, 스레드 수, 메모리, OOM·재시작.
6. 재현 방법은 `K6_PERFORMANCE.md` 10절과 같고, 추가로 마이그레이션이 적용된 jar로 `backend-perf`를 다시 빌드해 띄운다. C2는 `PERF_COMPOSE_EXTRA=infra/k6/compose.plan-cache.yml`을 주고 `run-measure.sh`를 실행한다(재기동 때도 설정이 유지되게 하는 환경 변수).

| 검색 전체(15개 + 15개) | 68.2 / 79.3 | 64.8 / 126.4 | **37.9 / 68.9** |
| 2글자 연속 구간(S1b) | 66.1 / 75.0 | 121.5 / 134.1 | 66.9 / 76.2 |

- C1의 3글자 이상은 C0보다 평균 약 86% 빨라졌지만 2글자 이하는 약 77% 느려졌다. C2는 3글자 이상의 개선을 유지하면서 2글자 이하를 개선 전 수준으로 되돌렸다(3글자 이상 평균 약 85% 단축).
- 검색 전체 평균 68.2 → 37.9ms(약 44% 단축)는 **검색어가 2글자 이하와 3글자 이상 반반일 때의 값**이다. 실제 사용자의 검색어 분포에 따라 달라진다.
- 2글자 연속 구간은 세 구성 모두 20초 단위 평균이 평평했고 중간에 전환되는 시점이 보이지 않았다(C1은 처음부터 느림).
- 재기동 직후 첫 검색 요청은 세 구성 모두 218~296ms로 같은 범위였다(JIT·연결 준비로 추정, 계획 설정과 무관).
- 상세·인기 순위 API는 세 구성에서 p95 2.4~8.5ms로 같은 수준이었다.

### 7-2. 읽기 한계
| 지표 | C0 | C1 | C2 |
|---|---|---|---|
| 마지막 안정 단계 | 160 req/s | 160 | **275** |
| 느려지기 시작 | 170 | 170 | 300 |
| 무너진 단계(실제 req/s) | 180 (163.2) | 180 (175.7) | **325 (304.2)** |
| 무너질 때 전체 p95 | 2,705ms | 1,788ms | 2,303ms |
| 무너질 때 밀린 반복 / 스레드 | 146 / 223 | 85 / 158 | 713 / 223 |
| 메모리 최대(평상시 / 한계) MiB | 499 / 551 | 547 / 539 | 488 / 563 |

- 한계 시험은 읽기 p95가 1초를 넘으면 자동 중단하는 설정이라(`abortOnFail`) 세 구성 모두 이 조건으로 끝났다.
- **C1은 한계가 오르지 않았다.** 검색 1건이 DB 연결을 잡는 평균 시간이 C0(약 68ms)과 C1(2글자 이하 약 130ms와 3글자 이상 약 7ms의 평균 약 69ms)이 거의 같아서 빨라진 쪽과 느려진 쪽이 상쇄된 것으로 계산된다(추정).
- **C2는 한계가 크게 올랐다.** 검색 평균 점유가 약 38ms로 줄고, 연결 5개로 나누면 검색 약 133건/s, 검색이 40%인 요청 비율에서 전체 약 333 req/s가 되어 실제 붕괴(300~325)와 맞는다(계산, 풀 대기 수는 재지 않음).
- 나빠지는 순서는 세 구성 모두 같다. 검색 응답 시간이 먼저 오르고, 목표 처리량을 못 따라가며 스레드가 쌓인다. 오류는 끝까지 0%였다. C2는 붕괴 단계에서 CPU 중앙값이 43%로 CPU가 포화된 것은 아니었고, 상세·인기도 약 670ms로 함께 느려졌다(스레드가 한계 가까이 쌓여 모든 요청이 줄을 선 것으로 보지만 확인하지 못했다).
- C2 한계 측정 중 한 번은 서버를 다시 띄운 직후 10초 안에 5건에서 200건으로 올려 CPU가 97%까지 치솟은 채 22초 만에 멈췄다. 한계가 아니라 데워지기 전 급상승 때문으로 보고 무효로 처리한 뒤 단계를 나눠 다시 쟀다.

### 7-3. 이 결과로 말할 수 있는 것과 없는 것
- 말할 수 있는 것: 같은 날 같은 환경에서 3글자 이상 검색이 약 85% 빨라졌고, 인덱스만으로는 2글자 이하가 느려지지만 매번 계획 세우기를 더하면 개선 전 수준으로 돌아오며, 읽기 마지막 안정 단계가 160에서 275 req/s로 올랐다.
- 말할 수 없는 것: 운영 환경의 절대 수치(로컬은 DB가 같은 호스트에 있고 CPU가 더 강하다), 한계 숫자의 반복 안정성(범위마다 1회), 서버가 실제로 사용자 정의 계획을 썼는지의 직접 증거(응답 시간으로 추정), 매번 계획 세우기가 검색 외 쿼리에 주는 영향(읽기 API 평상시만 확인).

## 8. 남은 한계와 다음 후보
1. **1글자 검색 제한(이번 개선 PR에서 구현).** 한글 검색은 2글자 이상이 대부분이고, 1글자는 결과가 지나치게 많아 의미 있는 검색이 되기 어렵다. 인덱스도 3글자 미만에는 도움이 되지 않는다(4-4). 그래서 검색어를 **최소 2글자**로 제한한다. 공백만 입력은 이미 막혀 있고 앞뒤 공백은 이미 잘라 낸다. 이 변경은 API 계약을 바꾸므로 한 곳만 고치지 않았다.

   | 고칠 곳 | 내용 |
   |---|---|
   | `docs/api/openapi.yaml` | 검색어 `q`의 `minLength`를 1에서 2로 변경 |
   | 백엔드 검증 | 2글자 미만이면 검증 오류로 응답 |
   | `docs/api/error-codes.md`, 프론트 `errorMessages.ts` | 화면에 보이는 오류 문구를 서로 일치 |
   | 프론트 탐색 화면 | 2글자 이상 입력 안내 |
   | 계약 검사 테스트 | 생성 명세와 `openapi.yaml`이 같아야 CI가 통과 |

   1글자 검색은 이번 측정 범위에서 제외했다(제한하면 측정할 필요가 없어진다).
2. 2글자 검색의 비용을 더 줄이는 방법: 개수 쿼리를 없애면(목록 쿼리만 남김) 순차 스캔이 한 번으로 줄어 약 40% 절감이 예상된다(81ms 중 32ms). 다만 응답에 전체 건수가 들어 있어서 계약 영향 확인이 필요하다. 이번에는 하지 않는다.
3. 계산 동시 실행 수 제한(혼합 부하에서 계산이 읽기를 굶기는 것을 막음), GC 조정(운영 JVM의 GC 종류 미확인): 효과가 작거나 근거가 약해 이번에는 기록만 한다.
4. 스트레스 스크립트의 상세 조회(미스) 시나리오는 키 선택 방식 때문에 600개만 반복하고 사실상 캐시에 맞는다. 세 구성 모두 같은 조건이라 이번 비교에는 영향이 없지만, 읽기 한계에서 DB를 쓰는 상세 경로가 약하게 반영되어 있다.
5. 확인하지 못한 것: 연결별 계획 전환 시점, 서버가 실제로 쓴 계획(`pg_stat_statements` 등), DB 연결 풀 대기 수, 붕괴 원인이 풀인지 Tomcat 스레드 상한인지.

## 9. 정리: 측정으로 병목을 찾고 고친 과정

운영과 같은 조건(메모리 1GiB, CPU 1개)의 환경을 도커로 만들고 k6로 부하를 걸어 서비스의 한계를 측정했다. 읽기 요청을 단계적으로 올리는 시험에서 검색이 먼저 무너졌고 그때 CPU는 30%대였다. `EXPLAIN ANALYZE`로 검색이 작품 3만여 건을 두 번 순차 스캔하는 것을 확인했고, 트라이그램 인덱스를 실험해 3글자 이상 검색이 32.9ms에서 0.14ms로 줄어드는 것을 확인했다. 2글자 이하에는 인덱스가 도움이 되지 않았다.

그다음 같은 날 같은 조건으로 세 구성을 측정했다. 인덱스만 넣으면 3글자 이상은 68.7ms에서 9.6ms로 빨라졌지만, 2글자 이하는 67.7ms에서 119.9ms로 오히려 느려졌고 읽기 한계는 그대로였다. 원인은 PostgreSQL이 같은 쿼리를 반복하면 계획을 하나로 굳히는데, 굳힌 범용 계획의 견적이 2글자에서 틀려(견적 1,025 대 4,059, 실제 59ms 대 30ms) 인덱스 경로를 타기 때문이었다. 연결마다 계획 방식을 고정하는 설정을 더하자 2글자 이하는 65.5ms로 돌아오고 3글자 이상은 10.3ms를 유지했으며, 읽기 마지막 안정 단계는 160에서 275 req/s로 올랐다. 후속으로 1글자 검색을 제한한다.

### 이 결과를 읽을 때의 주의
1. "검색이 가장 큰 문제"가 아니라 **읽기 API 중** 가장 먼저 한계에 도달한 것이 검색이다. 계산은 별개로 CPU 1코어가 상한이었다.
2. 개선 효과는 **글자 수 범위를 밝혀** 읽는다. 3글자 이상은 빨라졌고, 2글자 이하는 매번 계획 세우기가 있어야 개선 전 수준을 유지한다.
3. 로컬 측정이라 절대 수치는 운영과 다르다(운영은 CPU가 훨씬 약하고 DB가 네트워크 너머다). 같은 날 **상대 비교**가 근거다.
4. 읽기 한계는 범위마다 1회 측정이다.
5. 처음 발견 시점의 값(120/140)과 같은 날 A/B의 개선 전 값(160/180)이 다르며, 이유는 확인하지 못했다(2-2).

### 이 과정의 순서
측정으로 병목을 찾고(한계 찾기) → 지표로 원인 후보를 좁히고(CPU 30%대, 다른 API는 정상) → 실행 계획으로 확인하고(순차 스캔) → 실험으로 해결책의 효과와 한계를 검증하고(트라이그램, 2글자 한계) → 같은 조건에서 전후를 비교하다가 → 예상하지 못한 부작용(2글자 느려짐)을 발견해 원인을 규명하고(계획 캐시) → 설정을 더해 다시 측정했다. 한계와 부작용까지 기록해 둔 것이 이 기록의 신뢰 근거다.
