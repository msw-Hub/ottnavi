# k6로 찾은 검색 병목과 개선 과정

> 설명·기록 문서이고 근거 문서가 아니다. 측정 방법과 전체 결과는 `K6_PERFORMANCE.md`에 있고, 이 문서는 그중 **검색 문제 하나를 끝까지 따라가는 이야기**다.
> 진행 상태(2026-11-03): 문제 확인·원인 분석·실험까지 끝났고, **인덱스를 실제로 적용한 뒤의 전후 측정은 아직 하지 않았다.** 그 결과는 7장에 채운다(채우기 전에는 "개선했다"고 쓰지 않는다).

## 1. 한눈에 보기

운영과 같은 조건(메모리 1GiB, CPU 1개)의 로컬 컨테이너에 k6로 부하를 걸었더니, 읽기 API 중 **검색이 가장 먼저 무너졌다.**

| 단계 | 내용 | 핵심 숫자 |
|---|---|---|
| 1. 발견 | 초당 요청을 올리는 시험에서 140건 단계에 응답 시간이 급증 | p95 210ms(120건) → 2,902ms(140건) |
| 2. 원인 추적 | 그때 CPU는 30%대, 느려진 것은 검색뿐 | 검색 p95 426ms → 3,350ms, 상세·인기 순위는 2~4ms 유지 |
| 3. 가설 확인 | 검색이 작품 33,004건을 두 번 순서대로 읽음 | `EXPLAIN ANALYZE`: 순차 스캔 49ms + 32ms |
| 4. 해결책 실험 | 트라이그램 인덱스를 측정 DB에서 시험 | 3글자 한글 32.9ms → **0.14ms**, 2글자 한글 30.7ms → 31.2ms(변화 없음) |
| 5. 적용·전후 비교 | 마이그레이션으로 적용하고 같은 조건으로 재측정 | 7장(미측정) |

## 2. 문제를 발견하기까지

### 2-1. 무엇을 쟀나
k6는 가짜 사용자를 대량으로 만들어 서버에 요청을 보내는 도구다. 운영과 같은 조건의 측정용 컨테이너(복사한 DB 포함)에 다음을 걸었다.

1. 평소 속도: 검색 73ms, 상세 2~7ms, 홈 인기 순위 2ms, 평상시 계산 약 40ms.
2. 최악 입력 계산: 3.7초(CPU 1코어를 혼자 사용).
3. **한계 찾기**: 읽기 요청(검색 4 : 상세 3 : 인기 순위 3)을 초당 10건부터 단계적으로 올리고, 오류가 1%를 넘거나 응답 시간(p95)이 1초를 넘으면 자동으로 멈추게 했다.

### 2-2. 한계 찾기에서 일어난 일
같은 시험을 3회 반복했고 3회 모두 **초당 160건 단계에서 멈췄다.** 멈춘 단계 주변을 더 잘게 나눠 다시 쟀다(1회).

| 목표 req/s | 실제 req/s | 응답 p95 | 검색 p95 | 밀린 반복(dropped) | 스레드 | CPU 중앙값 |
|---|---|---|---|---|---|---|
| 80 | 80.0 | 121ms | 141ms | 0 | 35 | 74% |
| 100 | 99.9 | 138ms | 202ms | 0 | 37 | 32% |
| 120 | 120.0 | 210ms | 426ms | 0 | 50 | 31% |
| **140** | **84.6** | **2,902ms** | **3,350ms** | 149 | **203** | 33% |

**마지막으로 안정했던 단계는 120건, 무너진 단계는 140건**이다. 순서는 이렇다.
1. 검색 응답 시간만 먼저 오른다(80건에서 141ms → 120건에서 426ms).
2. 140건에서 처리량이 목표(140)를 못 따라가 84.6건에 머물고, 밀린 반복이 149건 생기며, 요청을 처리하는 스레드가 35개에서 203개로 쌓인다.
3. 오류는 끝까지 0%였다(느려지기만 했다).

### 2-3. 이 숫자가 알려 주는 것
| 관찰 | 의미 |
|---|---|
| 무너지는 순간에도 CPU 중앙값이 30%대 | 서버가 계산에 지친 것이 아니다. CPU가 원인이 아니라는 신호 |
| 같은 시점에 상세·인기 순위(Redis 캐시 경로)는 p95 2~4ms 그대로 | 서버 전체가 느려진 것이 아니라 **검색 경로만** 막혔다 |
| 스레드가 200개 이상 쌓임 | 요청들이 무언가를 기다리며 줄 서 있다 |
| 메모리 여유 491MiB 이상, GC 비중 2.1% 이하 | 메모리·GC 문제가 아니다 |

그래서 "검색이 쓰는 데이터베이스 경로 어딘가가 막힌다"는 가설을 세웠다.

## 3. 원인을 좁히기

### 3-1. 코드에서 본 것
검색은 제목·원제에 검색어가 **들어 있는** 작품을 찾는다(`TitleRepository.searchByTitle`).
```sql
-- 목록 쿼리 (한 페이지)
select * from title
where title ilike '%검색어%' or original_title ilike '%검색어%'
order by (개봉 시기 그룹), popularity desc ...
-- 개수 쿼리 (전체 건수)
select count(*) from title
where title ilike '%검색어%' or original_title ilike '%검색어%'
```
검색어 **앞에도 `%`가 붙어서**(중간 일치) 일반 인덱스(B-tree)로는 찾을 수 없고, `title` 표에는 기본키와 `(media_type, tmdb_id)` 인덱스뿐이다. 그리고 한 번의 검색 요청이 이 조건의 쿼리를 **두 번** 보낸다(목록, 개수).

### 3-2. 실제 실행 계획으로 확인
측정 DB에서 `EXPLAIN ANALYZE`를 돌렸다.

| 쿼리 | 실행 방식 | 걸린 시간 |
|---|---|---|
| 목록 쿼리 | `Seq Scan on title`(전체 순서대로 읽음, 32,364행을 걸러냄) | 49ms |
| 개수 쿼리 | `Seq Scan on title` | 32ms |

검색 한 번에 작품 33,004건을 **두 번 처음부터 끝까지** 읽는다. 동시에 요청이 몰리면 이 두 쿼리가 DB 연결(최대 5개)을 오래 붙잡고, 나머지 요청은 줄을 서서 스레드가 쌓인다. (여기까지는 지표와 실행 계획으로 **확인한 것**이다. "연결 5개가 모자라서 줄을 선다"는 설명은 풀 대기 수를 재지 않아서 **추정**이다.)

## 4. 해결책 고르기와 실험

### 4-1. 어떤 인덱스인가
앞뒤에 `%`가 붙은 검색은 **트라이그램(trigram) 인덱스**가 다룬다. 글자를 세 글자씩 겹쳐 쪼개서 인덱스에 담는다.
```
'기생충' → 기생충 (3글자라 조각 1개)   'avengers' → ave, ven, eng, nge, ger, ers ...
```
검색어도 같은 조각으로 쪼개 "이 조각들을 모두 가진 작품"을 인덱스에서 바로 찾는다. PostgreSQL의 `pg_trgm` 확장이 제공하고(`gin_trgm_ops`), **쿼리를 바꾸지 않아도** 같은 `ilike '%…%'`가 인덱스를 탄다.

### 4-2. 실험 방법
측정 DB에서 **트랜잭션 안에 인덱스를 만들고 계획을 본 뒤 되돌렸다.** 측정 DB에는 아무 흔적도 남지 않았다(확인: 인덱스 목록이 실험 전과 같음).

### 4-3. 결과 (개수 쿼리 기준)
| 검색어 | 인덱스 없음 | 인덱스 있음 | 계획 |
|---|---|---|---|
| 3글자 한글 `기생충` | 32.9ms | **0.14ms** | 인덱스 사용(Bitmap Index Scan) |
| 영문 긴 단어 `avengers` | - | 0.21ms | 인덱스 사용 |
| 영문 `the`(결과 3,824건) | - | 5.6ms | 인덱스 사용(결과가 많아 느림) |
| **2글자 한글 `사랑`** | 30.7ms | **31.2ms** | **순차 스캔 그대로(인덱스를 못 씀)** |

- 인덱스 크기: 제목 5.6MB + 원제 6.1MB(표 28MB), 생성 시간 합쳐서 약 0.5초.
- 한글도 조각이 만들어지는 것을 확인했다(`기생충` → 조각 4개).

### 4-4. 2글자가 안 되는 이유
트라이그램은 **세 글자 조각**이라서 검색어가 두 글자 이하면 쪼갤 조각이 없고, DB가 어쩔 수 없이 전체를 읽는다. 작품 제목 중 2글자 이하가 1,545건(4.7%)이고, 한국어 검색은 2글자가 흔해서 **실제 효과는 사용자가 3글자 이상을 얼마나 검색하느냐**에 달려 있다. 검색어 분포는 개인정보 때문에 로그에 남기지 않아서 알 수 없다.

## 5. 적용 방법과 준비

### 5-1. 마이그레이션 초안 (Flyway V12, 저장소 파일이고 배포 때 자동 실행된다)
```sql
CREATE SCHEMA IF NOT EXISTS extensions;                          -- Supabase에는 이미 있어서 아무 일도 안 함, 로컬·테스트 DB에는 새로 만듦
CREATE EXTENSION IF NOT EXISTS pg_trgm WITH SCHEMA extensions;   -- 확장을 설치할 폴더를 명시
CREATE INDEX idx_title_title_trgm ON title USING gin (title extensions.gin_trgm_ops);
CREATE INDEX idx_title_original_title_trgm ON title USING gin (original_title extensions.gin_trgm_ops);
```
**이 문장들을 웹(Supabase 화면)에서 직접 실행하는 것이 아니다.** 마이그레이션 파일에 담겨 배포될 때 서버가 시작하면서 Flyway가 실행한다. 쿼리와 자바 코드는 바뀌지 않는다.

### 5-2. "검색 경로에 extensions가 있다"는 말의 뜻
위 초안의 `extensions.` 표기와 이어지는 개념이라 풀어 둔다.

| 용어 | 쉬운 뜻 |
|---|---|
| 스키마(schema) | DB 안의 폴더. 테이블·함수 등이 폴더별로 들어 있다(`public`, `extensions` 등) |
| 검색 경로(`search_path`) | 이름만 썼을 때 DB가 **어떤 폴더를 어떤 순서로 찾는지** 정한 목록. Supabase의 현재 값은 `"$user", public, extensions` |
| 확장(extension) | DB에 기능을 더하는 부품. `pg_trgm`은 세 글자 조각 검색 기능을 준다 |
| 연산자 클래스 | 인덱스가 데이터를 **어떤 규칙으로 쪼개 담을지** 정한 부품. `gin_trgm_ops`는 "세 글자 조각으로 GIN 인덱스에 담는 규칙"이고 확장을 설치할 때 생긴다 |

인덱스를 만들 때 `gin_trgm_ops`를 **이름만** 쓰면 DB가 검색 경로의 폴더를 차례로 뒤져 찾고, 어디에도 없으면 `operator class "gin_trgm_ops" does not exist` 오류로 마이그레이션이 실패한다(서버 기동 실패로 이어진다). 그래서 확장을 어느 폴더에 설치하는지가 중요하고, 초안은 설치 폴더(`extensions`)와 사용 위치(`extensions.gin_trgm_ops`)를 **둘 다 명시**해서 Supabase와 폴더가 없는 로컬·테스트 DB 양쪽에서 같은 파일이 동작하게 했다.

### 5-3. 운영 DB(Supabase)의 현재 상태 (2026-11-03 확인)
| 확인 | 결과 |
|---|---|
| `pg_trgm` 사용 가능 여부 | 사용 가능(기본 버전 1.6) |
| 설치 여부 | 처음 확인했을 때는 **설치 전**(설치된 버전 없음, 어느 폴더에도 없음). 이후 사용자가 5-4의 한 문장을 실행해 설치했고 설치 폴더가 `extensions`로 확인됐다(2026-11-03) |
| 검색 경로 | `"$user", public, extensions` |

### 5-4. 사전 준비(선택, 운영 DB에서 하는 유일한 수동 작업)
앱이 접속하는 DB 계정에 확장 **설치 권한**이 있는지는 확인하지 못했다(Supabase의 기본 `postgres` 계정은 보통 가능). 안전하게 가려면 개선을 배포하기 **전에** Supabase SQL Editor에서 **다음 한 문장만** 실행해 확장을 미리 설치해 둔다.
```sql
create extension if not exists pg_trgm with schema extensions;
```
- 인덱스 생성문은 실행하지 않는다(배포 때 마이그레이션이 한다).
- 확장 설치는 테이블·데이터를 바꾸지 않고, 인덱스가 만들어지기 전에는 `drop extension pg_trgm;`으로 되돌릴 수 있다.
- 미리 설치해 두면 마이그레이션의 `CREATE EXTENSION IF NOT EXISTS`는 건너뛰므로 권한 문제로 기동이 실패할 위험이 사라진다.

### 5-5. 위험과 확인 목록
| 위험 | 대응 |
|---|---|
| 확장 설치 권한 부족으로 마이그레이션 실패 → 서버 기동 실패 | 5-4의 사전 설치 |
| 로컬·CI(Testcontainers)에서 `extensions` 폴더가 없음 | 초안의 `CREATE SCHEMA IF NOT EXISTS`와 폴더 명시 |
| 수집 때 `title`을 쓰면 인덱스도 갱신해야 함 | 수집은 하루 수 번, 3만 3천 행 규모라 영향이 작을 것으로 예상(측정하지 않음) |
| 인덱스 생성 중 `title` 쓰기가 잠깐 막힘 | 생성 약 0.5초(측정 DB 기준), 33,192건 규모라 사실상 무시 가능 |

## 6. 개선 전후를 어떻게 비교하나

기존 측정에는 **검색어 글자 수 구분이 없었고**, 검색어 30개 중 21개(70%)가 1~2글자였다. 그대로 비교하면 3글자 이상의 개선 폭이 묻힌다. 그래서 다음처럼 한다.

1. **검색어를 글자 수별로 균형 있게 구성**한다(2글자 이하 15개, 3글자 이상 15개). 요청마다 글자 수 태그를 달아 결과를 분리해서 보고한다.
2. **같은 날 A/B**: 개선 전 코드로 먼저 같은 측정을 하고(검색 평상시 3회, 읽기 한계 세분), 마이그레이션을 적용한 뒤 같은 측정을 한다. 컨테이너 조건(1GiB, CPU 1, `-Xmx512m`)과 데이터는 동일하게 유지한다.
3. 비교 항목: 평상시 검색 응답 시간(글자 수별), 읽기 한계(마지막 안정 단계, 무너진 단계), 무너질 때 검색 p95, 스레드 수.
4. 성공 기준은 미리 정한다: 3글자 이상 검색은 평상시 p95가 한 자릿수 ms로 내려가고 읽기 한계 단계가 올라간다. 2글자 이하는 **변화 없음이 정상**이다.
5. 재현 방법은 `K6_PERFORMANCE.md` 10절과 같고, 추가로 마이그레이션이 적용된 jar로 `backend-perf`를 다시 빌드해 띄운다.

## 8. 남은 한계와 다음 후보
1. **2글자 이하 검색은 개선되지 않는다.** 사용자가 정한 방향: 한글 검색은 2글자 이상이 대부분이라 1글자는 검색을 제한하는 것이 맞다(공백만 입력은 이미 막혀 있고 앞뒤 공백은 이미 잘라 낸다). 1글자 제한은 계약(`minLength` 1 → 2), 백엔드 검증, 오류 문구, 프론트 안내를 함께 바꾸는 별도 작업이라 개선 PR과 **분리해서** 진행한다.
2. 2글자 검색의 비용을 줄이는 다른 방법: 개수 쿼리를 없애면(목록 쿼리만 남김) 순차 스캔이 한 번으로 줄어 약 40% 절감이 예상된다(81ms 중 32ms). 다만 응답에 전체 건수가 들어 있어서 계약 영향 확인이 필요하다.
3. 계산 동시 실행 수 제한(혼합 부하에서 계산이 읽기를 굶기는 것을 막음), GC 조정(운영 JVM의 GC 종류 미확인): 효과가 작거나 근거가 약해 이번에는 기록만 한다.

## 9. 정리: 측정으로 병목을 찾고 고친 과정

운영과 같은 조건(메모리 1GiB, CPU 1개)의 환경을 도커로 만들고 k6로 부하를 걸어 서비스의 한계를 측정했다. 읽기 요청을 단계적으로 올리는 시험에서 초당 120건까지는 안정적이었고 140건에서 응답 시간이 급증했다. 그때 CPU는 30%대였고 느려진 것은 검색 API뿐이었다. `EXPLAIN ANALYZE`로 검색이 작품 3만여 건을 두 번 순차 스캔하는 것을 확인했고, 트라이그램 인덱스를 실험해 3글자 이상 검색이 32.9ms에서 0.14ms로 줄어드는 것을 확인했다. 2글자 이하에서는 인덱스가 동작하지 않는다는 한계도 함께 확인했고, 후속으로 최소 검색 글자 수 제한과 개수 쿼리 정리를 검토하기로 했다. (적용 후 재측정 결과는 7장을 채운 뒤 이 문단의 숫자와 함께 갱신한다.)

### 이 결과를 읽을 때의 주의
1. "검색이 가장 큰 문제"가 아니라 **읽기 API 중** 가장 먼저 한계에 도달한 것이 검색이다. 계산은 별개로 CPU 1코어가 상한이었다.
2. 개선 효과는 **글자 수 범위를 밝혀** 읽는다(3글자 이상). 2글자 이하는 효과가 없었다.
3. 로컬 측정이라 절대 수치는 운영과 다르다(운영은 CPU가 훨씬 약하고 DB가 네트워크 너머다). 개선 전후 **상대 비교**가 근거다.
4. 개선 효과의 숫자는 7장의 전후 측정이 끝난 뒤에만 확정한다.

### 이 과정의 순서
측정으로 병목을 찾고(한계 찾기) → 지표로 원인 후보를 좁히고(CPU 30%대, 다른 API는 정상) → 실행 계획으로 확인하고(순차 스캔) → 실험으로 해결책의 효과와 한계를 검증하고(트라이그램, 2글자 한계) → 같은 조건에서 전후를 비교한다. 한계까지 기록해 둔 것이 이 기록의 신뢰 근거다.
