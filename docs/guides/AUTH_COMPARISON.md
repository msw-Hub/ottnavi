# 인증·인가 방식 비교: swr → 세나하자 → 코드한사바리 → ottnavi

> 2026-10-16 작성. 사용자가 만든 이전 프로젝트 세 개와 이번 ottnavi 설계를 같은 눈높이로 비교한 설명 문서다. 근거 문서가 아니고 코드가 기준이다(규칙의 근거는 `docs/TECH.md` 4절, T-7, PRD R11-21).
> 이전 프로젝트 내용은 코드를 읽은 결과이고(실행하지 않음), 시크릿 값은 읽지 않았다. 당시 선택의 이유는 사용자의 설명이다.

## 1. 먼저 용어 (건물 출입 비유)

로그인을 "회사 건물에 들어가는 일"로 보면 쉽다.

| 용어 | 비유 | 하는 일 |
|---|---|---|
| Access Token(AT) | **출입증** | 서버 문(API)을 열 때마다 보여 준다. 짧게 쓰고 만료된다. |
| Refresh Token(RT) | **출입증 교환권** | 출입증이 만료되면 새 출입증으로 바꿔 받는 데 쓴다. 오래 간다. |
| 쿠키(HttpOnly) | **잠긴 주머니** | 브라우저가 알아서 들고 다니고, 화면의 스크립트(JS)는 열어 볼 수 없다. |
| 블랙리스트 | **분실 장부** | "이 번호의 출입증은 무효"라고 적어 두는 명단 |
| 회전 | **교환권 일회용화** | 교환권을 한 번 쓰면 새 교환권을 주고 옛것은 버린다. |
| 계열(family) | **교환권 묶음** | 로그인 한 번에서 시작해 회전으로 이어지는 교환권들의 줄. 기기(브라우저)마다 따로 생긴다. 노트북과 폰에서 각각 로그인하면 계열이 두 개다. |

## 2. 네 프로젝트를 한 장으로

| 항목 | swr | 세나하자 | 코드한사바리 | ottnavi (이번) |
|---|---|---|---|---|
| 로그인 | 이메일·비밀번호 + 카카오(직접 호출) | 관리자 이메일·비밀번호 | Google OAuth2 | Google OAuth2 |
| 출입증(AT) | JWT 10시간 | JWT 6시간(하나뿐) | JWT 15분 | JWT 30분 |
| 교환권(RT) | JWT 7일, DB 컬럼 1개 | **없음** | JWT 14일, Redis에 1개 | 불투명 문자열 14일, Redis(해시) |
| 클라이언트 보관 | 응답 헤더(JS가 읽음) | 쿠키 | 쿠키(둘 다) | AT는 메모리, RT는 쿠키 |
| 재발급 | 필터 안에서 401로 신호 | 없음(재로그인) | AT만 새로 발급 | 매번 RT 회전 |
| 로그아웃 | DB 블랙리스트 | Redis 블랙리스트(전체 기기) | Redis 블랙리스트 | 현재 기기 계열만 폐기 |
| 역할 | 사실상 USER 하나 | ROOT·EDITOR·VIEWER | USER·ADMIN·ROOT | USER·ADMIN |
| 오류 응답 | 제각각 | 기본 오류 형식 | 직접 만든 JSON | ProblemDetail 통일 |

## 3. 프로젝트별 이야기

### 3.1 swr: 처음 만든 방식

**비유**: 출입증(10시간)과 교환권(1주일)을 둘 다 직원 손에 쥐여 준다. 교환권 번호는 경비실 장부(DB)에 한 장 적어 둔다. 퇴근할 때 두 번호를 분실 장부(DB 표)에 적는다.

| 순서 | 일어나는 일 |
|---|---|
| 로그인 | 이메일·비밀번호(또는 카카오)가 맞으면 두 토큰을 **응답 헤더**로 준다. |
| 요청 | 프론트가 `Authorization: Bearer 토큰`을 매번 보낸다. |
| 만료 | 필터가 만료를 발견하면 새 출입증을 만들어 헤더에 담고 401로 응답한다. 프론트가 그걸로 다시 요청한다. |
| 로그아웃 | DB의 교환권을 비우고 두 토큰을 블랙리스트 표에 넣는다. |

배울 점: 서명 키를 AT용·RT용으로 따로 둔 것, RT를 DB에 저장해 서버가 폐기할 수 있게 한 것. 서버가 토큰을 끊을 수 있다는 감각이 이 때 생겼다.
아쉬웠던 점: 헤더로 준 RT는 JS가 읽을 수 있어 XSS(악성 스크립트)에 약하고, 블랙리스트 표는 지워지지 않고 계속 커지며, 오류 응답이 제각각이었다.

### 3.2 세나하자: 관리자 전용이라 단순하게

**이유(사용자 설명)**: 관리자 권한(ROOT·EDITOR·VIEWER)에 따라 로그인을 다르게 해야 했고, 관리자 페이지라 **매번 새로 로그인하는 게 맞다**고 판단해 RT를 두지 않았다.

**비유**: 보안이 엄격한 사무실이라 교환권이 없다. 6시간짜리 출입증 하나를 잠긴 주머니(쿠키)에 넣어 주고, 시간이 지나면 다시 신분증 검사를 받는다. 퇴근하면 그 사람 이름으로 나간 출입증 전부를 분실 장부(Redis)에 적는다.

| 순서 | 일어나는 일 |
|---|---|
| 로그인 | 이메일·비밀번호(BCrypt)가 맞으면 JWT 하나를 **HttpOnly 쿠키**로 준다. |
| 요청 | 서버 필터가 쿠키를 읽어 서명·만료·블랙리스트를 확인하고 토큰 안의 role로 권한을 정한다. |
| 로그아웃 | 그 이메일의 활성 토큰 번호를 전부 블랙리스트에 넣고 쿠키를 지운다(모든 기기). |

배울 점: 목적에 맞게 RT를 과감히 뺀 판단, 쿠키 + Redis 블랙리스트로 저장소를 가볍게 옮긴 것.
아쉬웠던 점: 쿠키가 `SameSite=None`이라 다른 사이트에서의 요청에 약하고, 로그인 때 토큰 전체를 로그에 남긴 곳이 있었다.

### 3.3 코드한사바리: 프론트 요구 + Redis

**이유(사용자 설명)**: 프론트에서 **세션 쿠키 방식**을 원해서 쿠키로 시작했고, Redis를 붙인 김에 로그아웃 블랙리스트도 그렇게 관리해 봤다.

**비유**: 출입증(15분)과 교환권(14일)을 둘 다 잠긴 주머니에 넣어 준다. 교환권은 14일 동안 같은 것을 쓰고, 출입증이 만료되면 교환권을 보여 새 출입증만 받는다. 퇴근하면 두 번호를 분실 장부(Redis)에 적고 경비실 장부도 지운다.

| 순서 | 일어나는 일 |
|---|---|
| 로그인 | Google 인증 후 AT·RT를 둘 다 HttpOnly 쿠키(`Path=/`)로 준다. 성공 시 프론트 `/auth/callback`으로 이동. |
| 요청 | 필터가 블랙리스트 → 서명 → 종류 → 만료 → DB 사용자 → 활성 여부 → Redis 세션 순으로 확인한다(요청마다 DB·Redis 조회). |
| 만료 | `401 ACCESS_TOKEN_EXPIRED` + `canRetry: true`를 주고, 프론트가 재발급을 호출한다. |
| 로그아웃 | AT·RT 번호를 남은 수명만큼 블랙리스트에 넣고 Redis 키와 쿠키를 지운다. |

배울 점: 만료 이유를 오류 코드로 구분해 프론트가 쉽게 처리하게 한 것, 블랙리스트를 남은 수명만큼만 저장해 표가 커지지 않게 한 것, 역할을 DB에서 읽어 즉시 반영한 것.
아쉬웠던 점: 교환권이 회전하지 않아 탈취되면 14일간 유효하다. 교환권 쿠키가 `Path=/`라 모든 요청에 실려 간다. 개발용 빠른 로그인 경로가 운영에도 열려 있을 가능성이 있었다(확인하지 못함).

## 4. ottnavi는 무엇이 다른가

**비유**: 출입증(30분)은 **직원 머릿속(프론트 메모리)**에만 둔다. 잃어버릴 주머니가 없다. 교환권은 **일회용 쿠폰**이고 잠긴 주머니(쿠키)에 넣되, 재발급 창구(`/api/auth`)에 갈 때만 꺼낸다. 쿠폰을 쓰면 새 쿠폰을 주고 옛 쿠폰은 폐기한다. **이미 쓴 쿠폰이 다시 나타나면 도난으로 보고 그 쿠폰 묶음 전체를 취소**한다. 금고(Redis)에는 쿠폰 원본이 아니라 **지문(해시)**만 보관한다. 같은 쿠폰을 거의 동시에 두 번 내면(탭 두 개) 10초까지는 봐준다.

| 이전 프로젝트의 약점 | ottnavi에서 |
|---|---|
| RT 회전·재사용 탐지 없음 | 매번 회전, 재사용 시 계열 무효화 |
| RT 쿠키가 모든 요청에 실림(`Path=/`) | `Path=/api/auth`로 재발급·로그아웃에만 실림 |
| `SameSite=None` + CSRF 방어 약함 | `SameSite=Lax` + 재발급·로그아웃에 Origin 검사 |
| 토큰·비밀번호가 로그에 남음 | 토큰·쿠키·`code`는 로그에 남기지 않는 규칙 |
| 운영에 열린 개발용 로그인 | 만들지 않는다(필요하면 local 프로필 한정) |
| 블랙리스트 표가 계속 커짐 | AT 블랙리스트를 두지 않음(30분 만료) |
| 오류 응답이 제각각 | ProblemDetail + `errorCode`로 통일 |
| RT 원문이 저장소에 그대로 | SHA-256 해시로 저장 |

### 4.1 로그아웃은 "현재 기기 계열만" 폐기한다

**계열(family)**은 로그인 한 번에서 시작해 회전으로 이어지는 교환권 묶음이다. 기기(브라우저)마다 로그인하면 계열이 따로 생긴다.

```
노트북에서 로그인 → 계열 A: a1 → a2 → a3 ...   (쓸 때마다 새 교환권으로 교체)
폰에서 로그인     → 계열 B: b1 → b2 ...
```

**노트북에서 로그아웃하면 일어나는 일**

| 순서 | 일어나는 일 |
|---|---|
| 1 | 노트북 브라우저가 `POST /api/auth/logout`을 부른다. 교환권 쿠키(`rt`)가 같이 간다. |
| 2 | 서버가 쿠키의 교환권에서 **계열 번호(familyId)**를 읽어 Redis의 `rt:fam:A`를 지운다. |
| 3 | 응답으로 쿠키를 지우라는 헤더(`Max-Age=0`)를 보낸다. |
| 4 | 계열 B(폰)는 그대로라서 폰은 계속 로그인된 상태다. |

| 방식 | 노트북에서 로그아웃하면 | 어울리는 곳 |
|---|---|---|
| **현재 기기 계열만 폐기**(ottnavi) | 노트북만 로그아웃, 폰은 유지 | 일반 사용자 서비스. 보통 "로그아웃"이 이 동작이다. |
| 전체 기기 폐기(세나하자) | 노트북과 폰 모두 로그아웃 | 관리자 페이지처럼 보안이 우선인 곳 |

**왜 이렇게 했나**
1. 일반 사용자가 폰에서 로그아웃했다고 노트북까지 풀리면 불편하다.
2. 계열마다 키가 따로(`rt:fam:{familyId}`) 있어서 한 계열만 지우는 것이 가장 단순하다.
3. "모든 기기 로그아웃"이 필요해질 때(탈퇴, 계정 도난 신고)를 위해 사용자별 계열 목록(`rt:user:{userId}`)을 함께 저장해 둔다. 기능은 2단계 탈퇴 때 만든다.

**알아 둘 점**: 로그아웃해도 이미 발급된 출입증(AT)은 만료(30분)될 때까지 유효하다. 그래서 AT를 프론트 메모리에만 두고, 로그아웃 때 프론트가 메모리의 AT도 같이 버린다.

## 5. 이전 경험에서 그대로 가져온 것

| 경험 | ottnavi 반영 |
|---|---|
| swr: RT를 DB에 저장해 두고 요청이 올 때 대조해서, 서버가 원하면 토큰을 끊을 수 있게 했다 | 같은 아이디어를 Redis에 저장한다(자동 만료 시간 TTL이 있고 빠르다). 저장된 목록에서 지우면 그 로그인은 즉시 끊긴다 |
| 한사바리: 블랙리스트를 남은 수명만큼만 | RT 키에 14일 TTL(회전마다 갱신) |
| 한사바리: 프론트가 재시도 여부를 알기 쉽게 | 401이면 재발급 한 번 시도, 실패하면 로그인 화면(오류 코드 세분화는 보류, Q9 = A) |
| 세나하자: 역할은 토큰에 담아 가볍게 | role을 AT에 담음(변경은 다음 재발급 때 반영, 최대 30분) |
| 세나하자: 목적에 맞게 줄이기 | 관리자 지정은 DB 직접 수정(R-5), 모든 기기 로그아웃·탈퇴는 2단계 |

## 6. 이번 설계가 받아들인 한계

1. **역할 변경이 최대 30분 늦게 반영**된다(AT 안에 역할이 있어서). 관리자가 본인 한 명이라 받아들였다.
2. **로그아웃 직후 AT가 30분 유효**하다(AT 블랙리스트가 없어서). 메모리에만 있고 짧아서 받아들였다.
3. **Redis가 멈추면 재발급·로그인이 실패**한다(500). 401로 바꾸면 정상 사용자가 로그아웃되므로 일부러 500으로 둔다. AT 검증은 Redis를 쓰지 않아 30분 동안 회원 API는 동작한다.
4. **Redis가 비워지면 모든 사용자가 다시 로그인**한다(TECH 4절에 기록된 한계).
