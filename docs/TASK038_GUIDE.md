## 2. 왜 하는가

1. **이 서비스의 핵심 가치가 이 규칙에 있다.** "찜한 작품을 예산·시청 시간 안에서 어느 달에 어디서 볼까"가 서비스의 답이다. 규칙이 모호하면 완전탐색과 그리디의 결과를 비교(FR-13)할 수 없고, 같은 입력에 같은 결과가 나온다는 보장(캐시 `input_hash`, 정답 테스트)도 깨진다.
2. **엔진을 순수 Java로 분리하는 이유**(backend.md): 프레임워크 없이 테스트가 빠르고 정답 케이스를 수없이 돌릴 수 있다. 완전탐색은 한 번에 최대 약 210만 번 평가를 돌리므로(TECH 1절) **평가 1회가 가벼워야** 한다.
3. **결정적(deterministic)이어야 한다.** 같은 입력은 항상 같은 결과여야 정답 테스트가 흔들리지 않는다. 그래서 정렬의 마지막 기준(`watchUnitId`)과 비교기의 마지막 기준(⑤ 달별 상품 ID 사전순)이 있다(TECH 1절, 도출).
4. **038을 먼저 하는 이유**: 039(Solver)는 038의 평가기를 "조합 하나를 점수로 바꾸는 함수"로 부른다. 이 함수가 틀리면 그 위의 모든 탐색이 틀린다.

## 3. 규칙 정리 (PRD 5.4·TECH 1절을 코드 관점으로 다시 쓴 것)

### 3.1 입력과 용어

| 용어 | 뜻 | 출처 |
|---|---|---|
| 시청 단위(watch unit) | 영화 1편 또는 드라마 시즌 1개. 필요 시간은 **분** | PRD 5.4 |
| 월 시청 가능 시간 | 한 달에 볼 수 있는 분(프리셋 8/15/30시간 = 480/900/1800분, 환산, 직접 입력) | PRD 5.4 |
| 상품(product) | 구독 선택지 하나. MVP는 STANDARD **단품 7개**(번들·광고형은 2단계). 엔진에는 "ID + 가격 + 구독 상태"로 들어오고, 시청 단위 쪽이 "이 단위를 볼 수 있는 상품 ID 집합"을 가진다 | ERD B, TECH 1절 |
| 우선순위 | MUST(꼭) / WANT(보고 싶음) / MAYBE(여유될 때) | ERD C |
| 월(month index) | 0 = 이번 달(확정), 1·2 = 다음 두 달(예상). **항상 3개월** | PRD 5.4 |
| 구독 상태 | 서비스별 SUBSCRIBED(이미 구독 중) / FREE(무료 이용) / 없음 | ERD C |

### 3.2 시청 가능 규칙
- 어떤 시청 단위를 어떤 상품으로 **볼 수 있으면** 그 상품은 그 단위의 시청 가능 상품이다. 단품이므로 그 서비스의 제공 상태가 AVAILABLE일 때다.
- **"모름"(UNKNOWN)은 시청 가능으로 세지 않는다.**
- FREE(무료 이용) 서비스: **비용 0인 상시 시청 가능**. 구독 조합에 넣지 않아도 모든 달에 볼 수 있다.
- SUBSCRIBED(이미 구독 중): **이번 달(0번째 달) 비용 0**. 평가기가 0번째 달에는 선택에 없어도 비용 0으로 시청 가능한 것으로 다룬다(D2). 1·2번째 달은 선택해야 유지되고 가격이 들며, 선택하지 않으면 해지로 본다(PRD 5.4).
- 번들은 하나의 가상 서비스로 다룬다(MVP에는 없지만 입력 모델이 막지 않게 둔다).

### 3.3 배정 규칙 (고정)
1. **정렬**: 시청 가능 상품이 없는 단위(NO_PROVIDER·UNKNOWN)는 시간을 쓰지 않으므로 **맨 뒤**(결과 목록의 순서만 바뀐다) → 우선순위(MUST → WANT → MAYBE) → 필요 분 **짧은 순** → `watchUnitId` 오름차순(마지막은 도출).
2. 정렬 순서대로 한 단위씩, **볼 수 있는 가장 이른 달**부터 그 달의 **남은 시청 시간**에 채운다.
3. **한 달 시청 가능 시간(M)보다 긴 시즌**은 **서비스와 상관없이**, 그 시즌을 볼 수 있는 상품이 선택된 **연속된 달**에 이어서 나눠 배정한다(B안, 2026-10-09 사용자 결정. 예: 1월 넷플릭스에서 앞부분, 2월 티빙에서 이어서). 선택된 달이 이어지지 않으면 나눌 수 없다. 달마다 어느 상품으로 본 분량인지를 기록한다(같은 달에 볼 수 있는 상품이 둘이면 ID가 작은 쪽, D9). 한 달에 여러 서비스를 함께 선택할 수 있고, 월 시청 가능 시간은 서비스와 무관하게 그 달 전체에서 센다.
   - **결정 1(실제 시청 달도 연속, 사용자 결정 2026-10-09)**: 이 서비스는 3개월을 효율적으로 보는 것에 더해 **몰아보는 개념**이 있어서 긴 시즌은 쭉 이어서 본다. 볼 수 있는 달이 이어져 있어도, 선택된 달 중 가운데 달의 배정이 0분(그 달 시간이 이미 찼음)이면 이어 보기가 끊긴 것으로 보고 나눌 수 없다. 이때는 미배정이고 일부 배정했던 시간은 풀린다.
   - **결정 4(한 달 최소 2시간, 사용자 결정 2026-10-09)**: 긴 시즌은 **마지막 조각을 제외하고 한 달에 최소 120분**(영화 한 편 정도)씩 나눠 본다(상수 `MIN_LONG_SEASON_SEGMENT_MINUTES = 120`). 시작 달의 남은 시간이 120분 미만이면 그 달에서 시작하지 않고 다음 달부터 시도한다. 이어 가는 달의 남은 시간이 잔여 분보다 적으면서 120분 미만이면 끊긴 것으로 본다. 마지막 조각은 120분보다 작아도 된다. 한계: M이 120 미만이면 긴 시즌은 시작할 수 없다.
4. 한 달 이내로 볼 수 있는 단위는 **나눠 보지 않는다**. 이번 달 남은 시간이 부족하면 다음에 볼 수 있는 달로 넘어간다(도출, D3).
5. **다 본 달에 점수**를 준다(긴 시즌이 3개월에 걸쳐도 다 본 달 한 번).
6. **3개월 안에 끝나지 않으면 배정하지 않는다**(미배정). 이때 일부 배정했던 시간은 **풀어 준다**(도출, D4).

### 3.4 목적함수 비교 (사전식, 큰 쪽이 좋다)
① `mustCompleted`(시청 완료한 MUST 수) 큰 쪽 → ② `score`(시청 완료한 WANT 2점, MAYBE 1점의 합, MUST는 ①에서 센다 — D5) 큰 쪽 → ③ `totalCost`(3개월 비용 합) **작은** 쪽 → ④ 비용까지 같으면 **조기 시청**: 달 0→1→2 순서로 "그 달까지(포함) 시청 완료한 MUST 수, 같으면 점수 합"을 비교해 먼저 다른 달에서 **큰 쪽**이 좋다(시청 완료 달은 `UnitResult.completedMonthIndex`, 점수는 그 달에 얻는다. 2026-10-10 사용자 결정, D6) → ⑤ 그래도 같으면 **결제를 미루는 쪽**: 달 0→1→2 순서로 그 달에 **새로 돈이 드는 상품 수**(FREE와 0번째 달의 이미 낸 SUBSCRIBED는 세지 않는다)를 비교해 먼저 다른 달에서 **적은 쪽**이 좋다(2026-10-09 사용자 결정, 2026-10-10에 ④에서 ⑤로 내려감, D6) → ⑥ 그래도 같으면 달별 상품 ID 사전순(결과를 항상 같게 하려는 도출).

### 3.5 남은 작품의 이유 코드
판정 순서 **NO_PROVIDER → UNKNOWN → BUDGET → TIME**, 맞는 첫 번째를 쓴다.

| 코드 | 조건 |
|---|---|
| NO_PROVIDER | 7개 서비스에서 모두 "없음"(NOT_AVAILABLE) |
| UNKNOWN | "있음"은 없고 "모름"이 하나 이상 있음 |
| BUDGET | 시청 가능 상품은 있으나 **선택된 구독 조합의 어느 달에도 그 상품이 없음**(도출) |
| TIME | 시청 가능 상품이 선택된 달이 있으나 **시청 시간이 모자라** 끝내지 못함(도출) |

## 4. 구조 제안 (이름·모양은 사용자가 정한다)

`engine`은 다른 패키지를 참조하지 않는다(backend.md). 엔티티를 import하지 않고, 엔티티와의 변환은 나중에 `plan`이 한다.

```
com.ottnavi.engine
├── model/        # Assignment, Evaluation, OttProduct, OttProductCondition, PlanInput, Priority, Selection, UnitReason, UnitResult, WatchUnit
├── rule/         # Evaluator(시청 가능·배정·이유 코드·비용), EvaluationComparator(목적함수 비교기)
└── (039에서) solver/
```

**입력**(record, 불변)
```java
enum Priority { MUST, WANT, MAYBE }               // score: WANT 2, MAYBE 1 (D5)
enum UnitReason { NO_PROVIDER, UNKNOWN, BUDGET, TIME }
enum OttProductCondition { NONE, SUBSCRIBED, FREE }  // 사용자의 현재 구독 상태

record WatchUnit(long id, Priority priority, int requiredMinutes,
                 Set<Long> watchableProductIds,    // 시청 가능 상품 ID. FREE 상품 포함 여부는 D1
                 boolean isProviderUnknown) {}     // NO_PROVIDER와 UNKNOWN을 가르는 용도
record OttProduct(long id, int monthlyPrice, OttProductCondition condition) {}
record PlanInput(List<WatchUnit> units, List<OttProduct> products,
                 int monthlyBudget, int monthlyWatchMinutes) {}
```
- **불변으로 만드는 방법**: record 필드가 `List`·`Set`이면 만든 뒤에 바깥에서 내용이 바뀔 수 있다(record는 필드 참조만 final이다). 정렬과 반복 평가의 결과가 달라지지 않도록 **compact constructor에서 `List.copyOf`·`Set.copyOf`로 방어적 복사**를 한다(`WatchUnit`의 `watchableProductIds`, `PlanInput`의 `units`·`products`, `Selection`, `UnitResult`의 `assignments` 모두). `List.copyOf`는 이미 불변 목록이면 복사하지 않아 비용이 작다. 이 처리는 D8(생성자에서 한 번 정렬해 불변으로 보관)의 전제다.
- **입력 검증(결정 3)**: 시청 가능 상품 ID가 `products`에 없으면 `PlanInput` 생성자가 예외를 던진다. `plan` 변환(Task 063)이 입력 단계에서 상품을 걸러낼 때(예: 쿠팡플레이 제외, R11-13) 시청 가능 상품 집합도 함께 걸러야 한다.
- **상품 수 한계**: 상품이 32개를 넘으면 `Evaluator` 생성자가 예외를 던진다(내부 비트마스크가 `int`라서). 2단계에서 64개까지 필요하면 `long`으로 넓힌다.
- **월 가격 상한**: 상품 월 가격은 0원 이상 100만 원 이하여야 한다(`OttProduct.MAX_MONTHLY_PRICE`, 넘으면 생성자 예외). 엔진이 비용을 `int`로 합산하므로 상품 최대 32개 × 3개월 × 100만 원 = 9,600만 원이 `int` 범위 안에 들도록 하는 상한이다. 상품 수 한계나 이 상한을 늘리면 합산 타입(`long`)을 다시 검토한다(사용자 결정 2026-10-09, PR #25 CodeRabbit 지적). DB 가격이 상한을 넘을 때 서비스 계층이 어떻게 처리할지는 `plan` 변환(Task 063)에서 정한다.

**한 번의 평가**: "구독 조합 = 달마다 선택한 상품 ID 집합 3개"를 받아 결과를 돌려준다.
```java
record Selection(List<Set<Long>> productIdsByMonth) {}  // 길이 3
record UnitResult(long watchUnitId, boolean scheduled, Integer completedMonthIndex,
                  UnitReason reason, List<Assignment> assignments) {}   // 미배정이면 reason
record Assignment(int monthIndex, long productId, int minutes) {}   // 어느 상품으로 본 분량인지(서비스가 달마다 다를 수 있음, D9). MVP는 단품 1:1이라 서비스는 productId에서 정해지고(plan이 ott_service_id로 변환), 번들을 지원하는 2단계에 ottServiceId 필드를 추가한다
record Evaluation(Selection selection,   // 평가한 구독 조합. 비교기 ⑤(결제 미루기)·⑥(상품 ID 순, D6)가 이 값을 쓴다(④ 조기 시청은 `units`의 시청 완료 달을 쓴다)
                  int mustCompleted, int score, int totalCost, List<UnitResult> units) {}

// 호출 형태: 입력 하나로 평가기를 한 번 준비하고 조합마다 evaluate만 반복 호출한다(039의 Solver가 부른다)
// Evaluator evaluator = new Evaluator(planInput);
// Evaluation e = evaluator.evaluate(selection);
// 비교: new EvaluationComparator(planInput.products()).compare(e1, e2) > 0 이면 e1이 더 좋다
```
- **예산 검사는 평가기의 일이 아니다.** 달마다 선택 상품의 가격 합이 `monthlyBudget` 이하인 조합만 Solver가 고른다(039). 평가기는 받은 조합을 그대로 평가한다(D7).

- 확인: `.\gradlew.bat compileJava`가 통과한다. `engine`에서 `com.ottnavi.<다른 패키지>`를 import하지 않았는지 검색한다.

### ③ 시청 가능 규칙
- "이번 달 이 단위를 볼 수 있는 상품이 있나"를 판정하는 함수. FREE는 선택 여부와 무관하게 볼 수 있고, SUBSCRIBED는 0번째 달에 선택과 무관하게 볼 수 있다(3.2).
- 확인: 5.1의 T12(FREE 상시 시청 가능)·T13("모름"은 시청 가능 아님) 테스트가 통과한다.

### ④ 배정 규칙 (`evaluate`의 핵심)
- 정렬(`PlanInput` 생성자가 한 번, 기준은 `WatchUnit.ASSIGNMENT_ORDER`) → 단위마다 가장 이른 달부터 → 일반 단위(한 달 이내) / 긴 시즌(연속 달 분할, 결정 1·4)으로 나눠 구현한다.
- 평가 1회가 O(n log n)이어야 하므로(TECH 1절) 단위 수에 대해 정렬 한 번 + 한 번 훑기를 목표로 한다.
- **규칙 구현부마다 PRD 5.4의 어느 규칙인지 한 줄 주석**을 남긴다(ROADMAP).
- 확인: T1·T2·T5~T10(배정·분할·정렬·시간 풀기)과 T15~T19(서비스가 달라도 이어보기, 같은 달 두 서비스, 연속 아님, 실제 시청 달 끊김, 한 달 최소 2시간)가 통과한다.

### ⑤ 이유 코드·점수·비용
- 미배정 단위에 3.5 순서로 이유를 붙인다. `score`·`mustCompleted`·`totalCost`를 계산한다(SUBSCRIBED는 0번째 달 0원).
- 확인: T3(BUDGET)·T4(NO_PROVIDER·UNKNOWN)·T11(구독 상태 비용)이 통과한다.

### ⑥ 목적함수 비교기
- `EvaluationComparator`(`new EvaluationComparator(input.products())`, `compare(e1, e2) > 0`이면 e1이 더 좋다). 3.4 순서대로 사전식. 결제 미루기(⑤, D6)는 가격·구독 상태가 필요해 상품 목록을 받고, 조기 시청(④, D6)은 시청 단위의 우선순위(MUST 여부·점수)가 필요해 시청 단위 목록도 받아야 한다(2026-10-10 변경: 생성자 인자가 `input.products()`만에서 시청 단위까지 늘어나므로 `new EvaluationComparator(input)` 같은 모양은 구현에서 정한다). 마지막 동점 기준(⑥)은 `Evaluation.selection`의 달별 상품 ID를 쓰므로 `Evaluation`이 평가한 `Selection`을 들고 있어야 비교기 하나로 판정할 수 있다(4절 record).
- 확인: T14(비교기, ④ 조기 시청과 ⑤ 결제 미루기, ⑥ ID 순 포함)가 통과한다.

## 6. 완전탐색이 부르는 방식과 성능 메모 (039 대비)
- 039의 완전탐색은 달마다 예산 이하 상품 부분집합(MVP 7개 단품이면 최대 128개)을 만들고 3개월을 중첩해서 순회한다 → 최대 약 128³ ≈ 210만 번 `evaluate`를 부른다(TECH 1절).
- 그래서 `evaluate`는 **새 객체를 많이 만들지 않고** 단위 정렬은 호출 밖(입력 준비 때 한 번)에서 해 두는 설계가 유리하다. 정렬은 `PlanInput` 생성자가 한 번 하고 불변으로 보관하며 `Evaluator`는 그 순서를 그대로 쓴다(D8). 상품 위치·비트마스크도 `new Evaluator(planInput)` 생성자에서 한 번만 만들고 `evaluate(selection)`만 반복 호출한다.
- 성능 측정은 040·Task 100에서 한다. 038에서는 **정확성이 우선**이다(최적화는 측정 뒤).

### 6.1 MVP와 2단계(번들·광고형)에서 같은 것과 달라지는 것
번들은 계산에서 "볼 수 있는 서비스가 여러 개인 상품 하나"로 다룬다(PRD FR-19, TECH 1절). 그래서 **평가기(038)는 그대로 쓰고, 조합을 만드는 부분(039)이 달라진다.** 혼동을 막으려고 나눠 적는다.

| 구분 | MVP (STANDARD 단품 7개) | 2단계 (단품 + 번들 + 광고형) |
|---|---|---|
| 평가기 `evaluate` (038): 배정 규칙·비교기·이유 코드 | 이 문서의 규칙 | **같다.** 상품이 가격과 구독 상태만 가지면 되므로 단품·번들을 구분하지 않는다 |
| 한 상품으로 볼 수 있는 서비스 | 항상 1개 | 번들은 여러 개 |
| 한 시청 단위를 볼 수 있는 상품이 둘 이상일 때 기록 | D9(상품 ID가 가장 작은 것) | 같다 |
| `Assignment`의 서비스 식별 | `productId`로 정해짐(단품 1:1). `plan` 변환이 `ott_service_id`를 채운다 | 번들이면 모호하므로 `ottServiceId` 필드를 추가한다(그때 `plan` 변환도 고친다) |
| 달마다 조합 수 (039) | 2⁷ = 최대 128. 3개월 약 210만 평가 | 2^P. 예: P=12면 달마다 4,096, 3개월 약 690억 평가라 완전탐색이 현실적이지 않다 |
| 조합 규칙 (039) | 상품끼리 겹치지 않아 어떤 부분집합이든 가능 | 같은 서비스를 볼 수 있는 상품이 여럿(단품·광고형·번들)이라 **같은 달 중복 결제를 허용할지** 정해야 한다 |
| 지배 조합 제거 (039) | 시청 가능 집합이 같은데 더 비싼 것 위주 | 번들이 여러 단품의 시청 가능 범위를 더 싸게 포함하는 경우가 생겨 규칙이 더 중요하고 복잡하다 |
| 그리디 전환 (039·R11-30) | 상한을 넘는 경우가 드물다 | 상한을 넘는 입력이 흔해진다 |
| 상품 수 한계 (038) | `Evaluator`는 `int` 비트마스크라 최대 32개. MVP는 7개라 여유 | 32개를 넘으면 생성자가 예외를 던지므로 `long`(64개)으로 넓힌다 |

- **지금 해야 할 일**: 038(평가기)은 번들을 신경 쓰지 않고 만든다. 039는 **MVP 조합 규칙만** 구현하고, 번들을 위한 일반화(중복 결제 규칙 등)는 미리 하지 않는다(과한 추상화 금지).
- **2단계에서 정할 것**: 같은 서비스를 볼 수 있는 상품의 같은 달 중복 허용 여부(PRD 11절 33번)와 후보 수 상한. 이 둘이 정해지면 039의 조합 생성을 다시 설계한다.
- 이 변환 가정(상품 1개 = 서비스 1개)이 깔린 곳은 `plan`의 입력 변환 코드이므로 그 자리에 주석으로 남겨 둔다.

## 8. 확인하지 못한 것 (이 Task에서 확인)
- D1~D9 중 D6(④ 조기 시청·⑤ 결제 미루기)을 뺀 나머지는 문서에 명시되지 않은 도출이라 구현하면서 모호하면 PRD 5.4와 대조해 이 표를 고친다.
- "다 본 달에 점수" 시 긴 시즌이 이번 달 중간에 끝나는 경우 같은 달의 남은 시간을 다른 단위가 쓸 수 있다고 본다(D4와 같은 맥락). 테스트로 한 번 더 확인한다.
- **서로 다른 서비스로 이어 보기**는 B안으로 확정했다(2026-10-09, T15). 그래서 "같은 상품 연속인지 같은 서비스 연속인지" 문제는 사라졌고 `OttProduct`에 서비스 ID가 필요 없다. 남은 한계: 두 서비스가 같은 시즌을 제공해도 **회차 구성이 다를 수 있다**(한쪽은 일부 회차만 제공 등). 지금 데이터는 시즌 단위 제공 여부만 가져서 구분하지 못하므로 "확인된 범위"라는 표현으로 감수한다(PRD 5.6).
- 번들·광고형(2단계)의 `in_ad_tier`만 시청 가능으로 보는 처리는 이 Task 범위가 아니다.
