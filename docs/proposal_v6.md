## 1. 한 줄 요약

찜한 작품과 **월 예산·월 시청 시간**을 넣으면, 국내 OTT 7곳 중 **어느 달에 어디를 구독해야** 보고 싶은 작품을 가장 많이 볼 수 있는지 3개월 계획으로 알려주는 서비스다.

- 대상 서비스: 넷플릭스, 디즈니+, 애플TV+, 티빙, 웨이브, 왓챠, 쿠팡플레이 (7개, 라프텔 제외)
- 이름의 뜻: 작품을 검색하면(목적지), 예산 안에서 갈 경로(구독 순서)를 안내하고, 작품이 빠지면 경로를 다시 찾는다(매월 재계산). 내비게이션과 같은 흐름이다.
- 도메인: `ottnavi.shop` (구매 전 갱신 가격 확인)

## 2. 왜 이 서비스인가

- 보고 싶은 작품은 여러 OTT에 흩어져 있고, 전부 구독하면 비싸다.
- "필요한 달에만 구독하고 해지"하려면 어느 달에 어디를 구독할지 직접 계산해야 하는데, 작품이 많아지면 손으로 하기 어렵다.
- 처음에는 "찜한 작품을 전부 보는 최저가"를 계산하려 했지만, 찜이 많으면 답이 "전부 구독"이 되어 의미가 없었다. 그래서 **예산과 시청 시간이라는 현실적인 한계 안에서 가장 많이 보는 계획**을 계산하는 문제로 바꿨다.
- 작품 검색, 제공처 조회는 이미 다른 서비스도 하므로 신규성으로 내세우지 않는다. 로그인 없이 쓰는 입구 기능으로 둔다.

## 3. 기능

### 로그인 없이 쓰는 기능
- 작품 제목 검색 → 7개 서비스 중 어디서 볼 수 있는지 (있음 / 없음 / 모름)
- 작품 상세: 줄거리, 출연진, 러닝타임, 드라마는 시즌별 제공처
- OTT별 독점 작품 목록 (2단계)

### 로그인 후 쓰는 기능 (메인)
1. **처음 설정**: 서비스마다 "구독 안 함 / 구독 중 / 무료 이용(가족 공유 등)"을 고르고, 월 예산과 월 시청 시간을 입력한다.
2. **찜하기**: 작품을 찜하고 우선순위를 정한다 (꼭 / 보고 싶음 / 여유될 때). 드라마는 시즌별로 찜한다.
3. **요금 확인**: 기본 요금표를 보여주고, 실제로 내는 금액이 다르면 직접 고친다.
4. **계산**: 3개월 계획이 나온다.
   - 이번 달은 확정, 다음 두 달은 예상
   - 달마다 구독할 서비스와 볼 작품
   - 못 보는 작품과 그 이유
   - 전부 구독할 때보다 아낀 금액
5. **저장**: 마음에 들면 저장한다. 저장한 계획이 "내 플랜"이 된다.
6. **매월**: 본 작품을 "다 봤음"으로 체크하면, 다음 달 계산에서 빠진다. 월초에 이번 달 할 일을 메일로 받는다 (2단계).

### 관리자 기능
- 요금제 등록·수정 (번들은 2단계)
- TMDB 제공처를 우리 서비스와 연결하는 매핑 관리
- 데이터 수집 실행과 이력 확인

## 4. 계산은 어떻게 하는가

| 항목 | 정한 내용 |
|---|---|
| 시청 단위 | 영화 1편 또는 드라마 시즌 1개 |
| 시청량 | 편수가 아니라 **시간**으로 센다. 같은 12부작도 60분 드라마와 24분 애니는 다르기 때문 |
| 러닝타임이 없을 때 | 영화 120분, 회차 45분, 애니 회차 24분으로 추정하고 "추정"이라고 표시 |
| 월 시청 시간 프리셋 | 가볍게 8시간 / 보통 15시간 / 많이 30시간, 또는 직접 입력 |
| 우선순위 | 1순위 "꼭" 작품을 최대한 다 보기 → 2순위 나머지 점수(보고 싶음 2, 여유될 때 1) → 3순위 비용 최소 |
| 예산·시청 시간 | 둘 다 필수 입력 |
| 구독 중·무료 이용 | 무료 이용은 비용 0으로 계속 볼 수 있고, 구독 중은 이번 달 비용 0 |
| 긴 시즌 | 한 달에 다 못 보면 같은 서비스를 연속으로 구독하는 달에 나눠 본다 |
| 계산 방법 | 가능한 조합을 전부 따져 보는 방식(정확해)과 달마다 가장 좋은 것을 고르는 방식(그리디)을 둘 다 만들어 결과와 속도를 비교한다. 기본은 정확해, 조합이 너무 많으면 그리디로 바꾼다 |

**못 보는 작품의 이유는 4가지다.** 아래 순서로 판정한다.

| 이유 | 뜻 |
|---|---|
| 7개 서비스에 없음 | 7곳 모두 "없음"으로 확인됨 |
| 제공처 정보 없음 | "있음"은 없고 "모름"이 있음 (데이터가 부족해서 확인 못 함) |
| 예산 부족 | 볼 수 있는 서비스는 있지만 예산 안에서 그 서비스를 구독할 달을 못 만듦 |
| 시청 시간 초과 | 구독은 하지만 시간이 모자라 3개월 안에 다 못 봄 |

## 5. 플랜의 상태 (계산 → 저장)

| 상태 | 뜻 |
|---|---|
| 임시 (DRAFT) | 계산만 하고 아직 저장하지 않은 결과. 사람마다 1개, 다시 계산하면 덮어쓴다 |
| 현재 (ACTIVE) | 저장한 "내 플랜". 알림과 매월 재계산의 기준 |
| 지난 (ARCHIVED) | 새 플랜으로 바뀌어 물러난 이전 플랜. 변경 내역 비교용 |

- 이렇게 나눈 이유: 조건을 바꿔 여러 번 계산해 봐도 저장하기 전까지는 "내 플랜"이 바뀌지 않게 하기 위해서다.
- 계산한 뒤 데이터가 갱신되면 저장이 막히고, 화면이 자동으로 다시 계산한 결과를 보여준다.
- 매월 자동 재계산은 임시 단계 없이 바로 새 플랜을 만든다 (2단계).

## 6. 데이터는 어디서 오는가

- 출처: **TMDB** 공식 API (제공처 정보는 JustWatch 기반). 화면마다 출처를 표시해야 하고, 비영리로만 쓸 수 있다.
- 저장한 데이터는 6개월 안에 다시 갱신하거나 지운다 (약관 원문 확인 완료).
- 정확도: 직접 표본 33건을 앱과 대조해 30건이 일치했다. 왓챠의 오래된 영화에서 틀린 경우가 있었다.
- 쿠팡플레이는 TMDB 데이터가 매우 적어 "데이터 부족" 서비스로 표시한다.
- 그래서 결과는 "확정"이 아니라 **"확인된 범위"**라는 표현을 쓴다.

## 7. 어떻게 만드는가 (기술 선택 요약)

| 영역 | 선택 | 이유 |
|---|---|---|
| 백엔드 | Java 17, Spring Boot 4.1, JPA, PostgreSQL | 내가 직접 작성. 3.x는 무료 지원이 끝나 4.1 사용 |
| 프론트 | React, TypeScript, Vite, Tailwind, shadcn/ui | AI가 작성하고 나는 흐름·디자인·인증 코드를 검토 |
| 프론트-백엔드 약속 | OpenAPI 명세(`docs/api/openapi.yaml`) | 이 명세로 프론트 코드를 자동 생성해, 양쪽이 같은 형식을 쓰게 한다 |
| 데이터 수집 | Spring Batch + OpenFeign | 하루 단위 수집, 실패하면 이어서 다시 실행 |
| 로그인 | Google 로그인 + JWT | 로그인 유지 30분, 재로그인 없이 연장 14일 |
| 캐시·요청 제한 | Redis, Bucket4j | 같은 계산 결과 재사용, 비로그인 남용 방지 |
| 알림 | 메일 (Gmail 또는 메일 API) | 2단계 |
| 관리자 보조 | Gemini 무료 등급 (Spring AI) | 3단계, 관리자 기능에만 사용 |

**배포 구성과 비용 (월 1만 원 이내)**

| 대상 | 서비스 | 비용 |
|---|---|---|
| 프론트 | Vercel | 무료 |
| 백엔드 | Cloudtype | 개발 중 무료, MVP 배포 때 Hobby(월 6,600원)로 전환 |
| DB | Supabase | 무료 |
| Redis | Redis Cloud | 무료 |
| 모니터링 | Grafana Cloud | 무료 (3단계) |

- 사용자는 `ottnavi.shop` 하나만 접속한다. `/api` 요청은 Vercel이 Cloudtype 백엔드로 넘겨준다. 그래야 로그인 쿠키가 막히지 않는다.
- **Cloudtype 무료 플랜은 매일 아침 꺼지고, 대시보드에서 직접 켜야 한다** (실사용 확인). 그래서 무료 기간에는 자동 수집을 끄고 필요할 때 직접 실행한다. 자동 운영은 Hobby 전환 이후부터다.

## 8. 개발 일정 (약 2개월)

| 단계 | 기간 | 하는 일 |
|---|---|---|
| 0. 준비 | 2~3일 | 문서(PRD·TECH·ERD) 완료, 계정·키 발급, 백엔드·프론트 프로젝트 세팅 |
| 1. MVP | 1~4주 | 1주: 프론트 화면 골격(가짜 데이터), 계산 엔진 시작, 배포 경로 확인 / 2주: 데이터 수집, 검색·상세 / 3주: 로그인, 찜, 요금 / 4주: 플랜 계산·저장, MVP 배포 |
| 2. 운영 기능 | 5~6주 | 매월 재계산, 알림 메일, 번들·광고형 요금제, 독점 목록, 탈퇴 |
| 3. 품질 | 7~8주 | 모니터링, 성능 측정, 관리자용 AI 기능, 정확도 안내, README·회고 |

**MVP 완료 기준.** 로그인해서 설정·찜·요금 확인 후 3개월 플랜을 계산하고 저장할 수 있다. 비로그인으로 검색과 상세를 볼 수 있다. 배포 환경에서 이 흐름이 동작한다.

**MVP에서 미루는 것.** 알림 메일, 매월 자동 재계산, 번들, 광고형 요금제, 독점 목록, 탈퇴, 모니터링, AI 기능.

**작업 방식.**
- 문서 → 로드맵(`docs/ROADMAP.md`) → 태스크 매니저 순서로 쪼갠다.
- 브랜치: `main`(배포) / `develop`(개발 통합) / `feature/*`(기능) / `hotfix/*`(긴급 수정). 상세 규칙은 `.claude/rules/git.md`를 따른다. 커밋은 한국어 Conventional Commits.

## 9. 결정 기록

### 내가 직접 정한 것
- 주제, 대상 서비스 7개, 프로젝트 이름(OTT내비)
- 로그인 필요(메인)·불필요(검색·상세) 구분, 메일 알림
- 구독 중·무료 이용 입력, 금액 직접 수정, 결제일 기본 1일
- 3개월 계획, 예산 필수, 시청량을 시간으로 계산
- 기술 스택 선택, 배포 구성, 월 1만 원 예산
- MVP 우선, 프론트 골격 우선 개발, 2개월 일정
- 디자인은 작업하면서 결정
- 브랜치 전략(Git Flow 축소판)

### 제안을 듣고 내가 승인한 것
| 결정 | 쉬운 설명 |
|---|---|
| "꼭" 작품 최우선 | 점수만 쓰면 "여유될 때" 4편이 "꼭" 1편보다 앞설 수 있어서 순서로 처리 |
| 계산과 저장 분리 (임시 플랜) | 계산해 보는 것만으로 내 플랜이 바뀌지 않게 |
| 이유 코드 4가지 | "데이터가 없어서 모름"과 "어디에도 없음"을 구분 |
| 광고형 요금제는 2단계 | MVP 범위를 줄이기 위해. DB는 미리 준비해 둠 |
| 플랜 삭제는 DB가 자동으로 정리 | 플랜을 지우면 딸린 데이터를 DB가 한 번에 지워 빠르고 빠뜨리지 않음 (탈퇴도 같은 방식) |
| 수집 배치는 예외적으로 트랜잭션 안에서 외부 호출 | 대신 한 번에 처리하는 양을 작게 해 DB 연결을 오래 잡지 않게 |
| OpenFeign 유지, 계산은 정확해 기본 + 그리디 대체 | 이미 정한 스택을 유지 |
| 로그인 유지 30분, 연장 14일 | 일반적인 범위의 값 |
| 백엔드 직접 접속 차단, 응답 캐시 금지 | 다른 사람의 로그인 응답이 캐시되거나, 프록시를 우회해 요청 제한을 피하는 것을 막음 |
| 알림은 앱이 1분마다 발송, 가입 안내는 즉시 | 알림 종류마다 생기는 시점이 달라서 |

### 아직 내가 정해야 하는 것
아래 수치와 기한은 확정값이 아니라 추천안이다.

| 항목 | 추천안 | 언제까지 |
|---|---|---|
| Cloudtype에서 Gmail SMTP 발송 가능 여부 | 1주차 배포 때 연결 테스트, 안 되면 메일 API로 전환 | 1주차 |
| 쿠팡플레이를 계산에 넣을지 | 넣고 "데이터 부족" 표시 | 2주차 (계산 엔진 완성 전) |
| 비로그인 요청 한도 | 일반 분당 60회, 검색으로 새 작품 수집은 분당 10회, 계산은 분당 10회 | 2주차 |
| 찜 상한 | 시청 단위 100개 | 계산 시간 측정 후 |
| 로그인 연장 토큰을 서버에 저장할지 | Redis에 저장 (로그아웃·강제 만료 가능) | 3주차 (로그인 개발 전) |
| 가입 안내를 한 번만 보이는 방법 | 저장 직후 화면 + 메일 1회, 별도 저장 없음 | 2단계 |
| "주 N회 × M시간" 입력 저장 방식 | 계산된 분만 저장 | 3주차 |
| 정확도 안내 페이지 | 정적 페이지 | 3단계 |
| 관리자 모니터링 범위 | 앱 안은 수집·알림 현황, 서버 지표는 Grafana 링크 | 3단계 |
| 오래된 임시 플랜 판정 개선 | MVP는 지금 방식, 2단계에 개선 검토 | 2단계 |
