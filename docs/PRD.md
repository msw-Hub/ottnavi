## 2. 제품 개요

OTT내비는 사용자가 찜한 작품과 월 예산·월 시청 가능 시간을 바탕으로, 국내 OTT 7곳(넷플릭스, 디즈니+, 애플TV+, 티빙, 웨이브, 왓챠, 쿠팡플레이) 중 어느 달에 어디를 구독하면 우선순위 높은 작품을 가장 많이 볼 수 있는지 3개월 단위로 계산하고, 매월 데이터를 갱신해 다시 계산한 결과를 계정 이메일로 알려주는 비영리 서비스다. 메인 기능(Google 로그인 필요)은 3개월 롤링 플랜(이번 달 확정 + 다음 두 달 예상, 달마다 볼 작품, 못 보는 작품과 이유, 전체 구독 대비 절감액)과 월초·변경 알림이고, 서브 기능(로그인 불필요)은 작품 검색과 제공처 조회, 작품 상세, OTT별 독점 제공 목록이다. 데이터 출처는 TMDB(JustWatch 기반)이며 화면마다 표기한다.

- **문제.** 작품마다 제공처가 달라, 필요한 달에만 가입·해지하려면 사용자가 조합을 직접 계산해야 한다. "찜 전체를 보는 최저가 조합"은 찜이 늘면 "전부 구독"으로 수렴하므로, "월 예산·월 시청 시간 제약 안에서 우선순위 점수 최대화"로 정의했다. 이 방식은 "한 달에 한 곳만 구독"도 같은 엔진으로 처리한다.
- **차별점.** 제공처 조회 자체의 신규성은 내세우지 않는다(포털, 키노라이츠 등). 대신 ① 로그인 후 무료로 쓰는 예산·시간·우선순위 기반 롤링 플랜과 월초 알림 ② 이미 구독 중·가족 공유 등 무료 이용 서비스와 실제 지불 금액 반영 ③ 출처·정확도 공개와 불확실 데이터의 "모름" 표시.
- **기술 과제와의 연결.** 플랜 계산(달마다 조합 최대 128개 × 3개월 가지치기 완전탐색 vs 그리디 비교), 재계산·알림(outbox, 상태 머신, 중복 방지), 데이터(수집 배치, 계층별 갱신, 시즌 단위 저장, 정확도 표본 검증, 3상태 모델), 공개 조회(캐시, 독점 사전 계산, 요청 제한), 로그인(OAuth2, 사용자 데이터 격리, 관리자 분리).
- **개발 방식.** 백엔드는 직접 작성, 프론트는 AI가 작성한다. 프론트 골격을 목업으로 먼저 세워 흐름을 확정하고, 화면에서 OpenAPI를 도출한 뒤 실제 API로 하나씩 교체한다. 기간은 약 2개월(준비 + MVP 4주 + 확장 4주), 운영비는 저예산(절약할수록 좋음)이다.

## 3. 목표와 비목표

**목표**: 정해진 예산·시청 시간 안에서 찜한 작품을 가장 많이 보는 구독 계획을 근거와 함께 제공한다.

- 예산·시청 시간·우선순위를 반영한 3개월 플랜 계산, 정확해와 그리디 결과 비교 기록
- 실제 구독 상태(구독 중, 무료 이용)와 실제 지불 금액 반영
- 매월 데이터 갱신 후 재계산, 월초와 계획 변경 시 이메일 알림
- 로그인 없는 작품 검색·상세·OTT별 독점 목록
- 데이터 정확도를 표본으로 검증해 수치와 한계를 공개
- 배포·CI·테스트까지 갖춘 운영 가능한 수준

**비목표**: 영상 재생·스트리밍 / 라프텔 등 7개 외 서비스와 해외 지역 / 대여·구매(개별 결제) 비용(구독 flatrate만 센다) / OTT 사이트 스크래핑·비공식 수집 / 오리지널(자체 제작) 여부 판별 / 리뷰·평점·커뮤니티 / 개인화 작품 추천 / 결제 대행 / 모바일 앱 / 상업적 운영(TMDB 약관상 비영리만). 일할·중도 해지 계산도 범위 밖이다.

**성공 기준.** MVP 완료 기준(9절)이 1차 기준이다. 정량 지표 후보(정답 테스트 통과, 정확해 대비 그리디 점수·비용 차이 기록, 정확도 수치 공개, k6 응답 시간)는 채택 여부와 수치를 사용자가 정한다. 성능 수치는 측정 후 확정한다.

## 4. 사용자와 시나리오

방문자는 로그인 없이 작품을 검색하고 제공처를 확인한다. 사용자(역할 USER)는 Google 로그인 후 필요한 시기에 필요한 곳만 구독하려 한다. 운영자(역할 ADMIN, 같은 로그인)는 데이터 수집과 요금제·번들을 관리한다.

- **S1** 방문자: 제목 검색 → 영화·드라마가 구분되고 작품마다 7개 서비스 제공 상태가 보인다. (FR-01, 02, 05)
- **S2** 방문자: 작품 상세·OTT별 독점 목록 조회 → 작품 정보, 시즌별 제공처, 서비스별 독점 작품이 출처와 함께 보인다. (FR-03, 04)
- **S3** 사용자: 로그인 후 온보딩에서 서비스별 구독 상태, 결제일, 월 시청 시간, 월 예산 입력 → 저장되고 구독 중·무료 이용 서비스의 작품은 "이미 시청 가능"으로 표시된다. (FR-06, 08, 10)
- **S4** 사용자: 작품 찜과 우선순위(꼭 / 보고 싶음 / 여유될 때) 지정 → 찜 목록에 저장된다. (FR-09)
- **S5** 사용자: 요금 확인 단계에서 할인 금액을 고치고 계산 → 3개월 플랜, 달마다 볼 작품, 남은 작품과 이유, 절감액이 보인다. (FR-11, 12)
- **S6** 사용자: 플랜 저장과 알림 켜기 → 이번 달 가입 서비스가 있으면 "가입 즉시 해지 예약 권장" 안내가 화면과 메일로 한 번 온다. (FR-14, 15, 16)
- **S7** 사용자: 본 작품을 "다 봤음"으로 체크하고 월초 메일 수신 → 본 작품을 뺀 재계산 플랜과 변경 이유를 본다. (FR-09, 14, 15)
- **S8** 운영자: 데이터 정기 수집과 변경 확인 → 제공처가 바뀐 작품이 반영되고 영향받는 플랜이 재계산된다. (FR-18, 20)
- **S9** 운영자: 요금제·번들 등록·갱신 → 적용 시작일 이후 계산부터 새 가격이 적용된다. (FR-19)

**사용 흐름.** 로그인·온보딩(서비스별 미구독/구독 중/무료 이용, 구독 중이면 요금제와 결제일(기본 1일), 시청 시간 프리셋 또는 직접 입력, 월 예산 필수) → 찜하기(검색·상세에서 찜과 우선순위) → 요금 확인(관리자 기본 요금표를 보고 실제 내는 금액이 다르면 수정) → 결과(예: "월 1만 5천 원으로 꼭 볼 작품 8편 중 8편, 전체 23편 중 17편", 이번 달 확정·다음 두 달 예상 카드, 남은 작품과 이유, 절감액, 데이터 기준일. 계산 결과는 임시 플랜 DRAFT) → 저장(DRAFT가 현재 플랜 ACTIVE가 됨)과 알림(월초 메일로 가입·해지 예약 확인과 볼 작품) → 매월 재계산(데이터 갱신과 시청 체크를 반영해 DRAFT 없이 새 ACTIVE, 바뀐 내용과 이유를 다음 월초 메일에 담음). 찜부터 재계산까지는 매월 반복된다.

### 5.1 공개 기능

- **FR-01 작품 검색.** 제목으로 검색하고, 작품은 TMDB ID + media_type으로 식별한다(ERD `UNIQUE(media_type, tmdb_id)`). 수용: 같은 제목의 영화와 드라마가 구분되어 조회된다 / DB에 없는 작품은 TMDB에서 단건 수집·저장 후 결과에 포함된다 / TMDB 호출이 실패하면 오류 대신 DB 결과만 반환한다.
- **FR-02 제공 상태 3상태.** 서비스별로 있음(AVAILABLE) / 없음(NOT_AVAILABLE) / 모름(UNKNOWN)을 표시한다. 구독(flatrate)만 "있음"이고, 드라마는 시즌 단위로, 작품·시즌별 제공처 조회의 flatrate에 그 서비스가 직접 들어 있는지로만 판정한다(discover는 후보 수집 전용). 수용: 대여·구매만 있으면 "있음"이 아니다 / KR 데이터가 없거나 구조적 공백(쿠팡플레이 영화)이면 "모름"이다(unknown_reason NO_KR_DATA / STRUCTURAL_GAP) / 제공처 표시마다 TMDB·JustWatch 출처가 붙는다 / 3상태는 색만이 아니라 모양·텍스트로도 구분된다.
- **FR-03 작품 상세.** 포스터, 줄거리, 장르, 개봉·방영일, 러닝타임, 주요 출연진, 제공처를 보여주고, 드라마는 시즌별 제공처와 시즌 총 시청 시간을 보여준다. 수용: 한국어 줄거리가 없으면 영어로 대체하고 표시한다(overview_lang) / 포스터는 TMDB 이미지 서버와 출처 표기 / 추정 러닝타임에는 "추정" / 출연진은 상위 10명.
- **FR-04 OTT별 독점 목록.** 독점 = "확인된 범위에서 7개 중 이 서비스에서만 구독으로 볼 수 있는 작품". 수용: 수집 배치 후 미리 계산한다(availability에서 계산해 캐시) / 구조적 공백 구간(쿠팡플레이 영화)은 판정에서 빼고 화면에 명시한다 / 데이터 부족 서비스(data_quality = INSUFFICIENT)는 목록 대신 안내를 보여준다 / "확인된 범위의 독점"으로 표현한다(재현율 미측정).
- **FR-05 비로그인 요청 제한.** 수용: 한도를 넘으면 429(`RATE_LIMIT_EXCEEDED`) / 단건 수집을 일으키는 검색은 더 낮은 한도 / 프록시 뒤에서도 실제 클라이언트 IP 기준 / 화면은 "잠시 후 다시 시도"로 안내 / 한도 수치는 미결정(11절 12번).

### 5.2 회원 기능

- **FR-06 Google 로그인.** 수용: 비로그인으로 회원 API를 호출하면 401, 공개 API는 로그인 없이 응답 / 최초 로그인에 계정 생성, 이후 조회(`UNIQUE(oauth_provider, oauth_subject)`) / URL에 토큰을 싣지 않고 Access Token은 메모리, Refresh Token은 HttpOnly 쿠키, 수명은 AT 30분·RT 14일이며 RT는 재발급 때 회전(TECH T-7) / 로그인이 필요한 동작을 비로그인으로 시도하면 로그인 후 원래 화면으로 돌아온다(도출).
- **FR-07 탈퇴.** 찜, 구독 상태, 가격 수정값, 플랜, 대기 중 알림을 삭제한다. 수용: 탈퇴 후 그 사용자 데이터가 조회되지 않는다 / PENDING 알림이 발송되지 않는다 / calc_run은 통계용으로 남고 plan_id만 NULL이 된다.
- **FR-08 내 구독 상태.** 서비스별 미구독 / 구독 중(SUBSCRIBED) / 무료 이용(FREE), 구독 중이면 요금제와 결제일. 수용: 결제일 기본값 1일 / 무료 이용은 비용 0인 상시 커버, 구독 중은 이번 달 비용 0이고 다음 달부터 유지·해지를 계산 / 미구독은 저장 행이 없다 / 번들 이용 시 구성 서비스들이 같은 상품을 가리킨다.
- **FR-09 찜·우선순위·시청 체크.** 찜 추가·삭제·목록, 우선순위 꼭(MUST) / 보고 싶음(WANT) / 여유될 때(MAYBE), "다 봤음" 체크(SCR-08 안에서). 수용: 중복 추가는 무시된다(`UNIQUE(user_id, watch_unit_id)`) / 다른 사용자의 찜은 조회되지 않는다 / "다 봤음"(watched_at) 작품은 다음 계산에서 빠진다 / 구독 중·무료 이용 서비스로 이미 볼 수 있는 작품은 별도 표시 / 드라마는 시즌 단위로 찜하고 화면에서 시즌을 고른다.
- **FR-10 월 시청 시간·월 예산.** 둘 다 필수다. 시청 시간 입력 방식은 5.4 참고. 수용: 둘 중 하나라도 없이 계산을 요청하면 400(`VALIDATION_FAILED`) / 프리셋 값은 설정으로 바꿀 수 있다.
- **FR-11 요금 확인·금액 수정.** 계산 직전 관리자 기본 요금표(번들 포함, MVP는 단품)를 보여주고 사용자가 금액을 고친다. 수용: 수정값은 사용자별로 저장되고 관리자 요금표는 바뀌지 않는다 / 결과에 "사용자 입력 가격"(price_source = USER_OVERRIDE)으로 표시 / 관리자 가격이 바뀌면 수정하지 않은 서비스만 새 가격을 따른다.
- **FR-12 3개월 플랜 계산.** 이번 달 확정·다음 두 달 예상, 달마다 볼 작품, 남은 작품과 이유, 전체 구독 대비 절감액을 보여준다. 규칙은 5.4. 수용: 정답이 알려진 테스트 입력에서 결과가 일치한다 / 계산 결과는 DRAFT로 저장되고 ACTIVE는 바뀌지 않는다 / "꼭" 작품이 빠지면 그 이유를 가장 먼저 보여준다 / 남은 작품마다 이유 코드 4가지 중 하나 / 절감액 = 전체 구독 비용(all_subscribe_cost) − 플랜 총비용(total_cost) / 데이터 기준일(data_as_of) 표시 / 이번 달 가입 서비스가 있으면 "가입 즉시 해지 예약 권장" 안내 / 문구는 "확인된 범위".
- **FR-13 정확해와 그리디 비교.** 수용: 테스트 입력 세트에서 같은 입력(input_hash)으로 두 알고리즘을 돌려 점수 차이, 비용 차이, 계산 시간을 calc_run에 기록한다 / MVP에서 한 번 이상 기록한다.
- **FR-14 플랜 저장·매월 재계산.** 수용: 저장하면 DRAFT가 ACTIVE, 기존 ACTIVE는 ARCHIVED가 된다 / 오래된 DRAFT는 저장이 막힌다(5.4 플랜 상태) / 매월 재계산과 알림은 ACTIVE만 대상이고, 재계산은 DRAFT 없이 새 ACTIVE를 만들어 이전 플랜과 연결한다(previous_plan_id) / 결과가 달라지면 변경 내용과 이유(예: 작품이 서비스에서 빠짐)를 change_summary에 남긴다 / MVP에서는 사용자가 직접 재계산·저장해 갱신한다.
- **FR-15 월초·변경 알림.** 월초 메일(이번 달 가입·해지 예약 안내, 볼 작품, 변경 이유), 이번 달 확정 플랜의 작품이 제공처에서 빠질 때 변경 알림, 저장 시 가입 안내(S6). 수용: 같은 알림은 dedupe_key(예: `MONTHLY:{userId}:2026-11`)로 한 번만 생성된다 / 다음 달 이후 변경은 월초 메일에 모은다 / 유형은 SUBSCRIBE_GUIDE / MONTHLY / PLAN_CHANGE / 실패하면 재시도한다 / 문구는 "확인된 범위".
- **FR-16 알림 설정·이력.** 수용: 끄면(notification_enabled = false) 알림이 생성되지 않는다 / 이력에 상태(PENDING 대기, SENT 발송, FAILED 실패)가 보인다.

### 5.3 운영·관리 기능

- **FR-17 관리자 권한 분리.** 수용: 일반 사용자가 관리자 API를 호출하면 403 / 화면 가드는 편의 기능이고 실제 검사는 백엔드가 한다.
- **FR-18 데이터 정기 수집·반영.** 범위와 주기는 5.5. 수용: GitHub Actions cron이 관리자 전용 토큰으로 관리자 API를 호출해 실행한다(MVP 배포 전에는 cron 없이 로컬에서 수집을 실행하고 운영 적재는 MVP 배포 때 한다, 11절 4번) / 같은 날짜·tier의 중복 실행은 막힌다 / 작품·시즌 단위로 판정하고 영화 러닝타임과 회차별 러닝타임을 저장하며 변경 이력(availability_change)을 남긴다 / 저장 데이터는 6개월 안에 갱신하거나 삭제한다(fetched_at 점검) / 제공처가 바뀌면 영향받는 ACTIVE 플랜을 재계산한다(2단계) / TMDB 제공처 → 7개 서비스·tier 매핑 관리(SCR-15)를 포함한다.
- **FR-19 요금제·번들 관리.** 수용: 가격에 적용 시작일이 있고 결과는 가격 스냅샷이라 과거 결과가 바뀌지 않는다 / MVP는 STANDARD 단품만, 광고형(AD tier)은 2단계 O3에서 번들과 함께 / 번들은 계산에서 하나의 가상 서비스 / 판매 종료 상품은 삭제하지 않고 active = false / 같은 상품의 가격 기간은 겹치지 않는다 / 가격은 운영자가 직접 입력한다(자동 수집 없음).
- **FR-20 운영 이력 조회.** 수용: 최근 수집 실행의 성공·실패와 처리 건수, 변경된 작품, 재계산 대상 플랜 수, 알림 발송 상태(2단계부터)가 보인다 / 수집 이력은 Spring Batch 메타데이터를 읽기 전용으로 조회한다.
- **FR-21 데이터 정확도 안내.** 수용: 8.2의 검증 방법·결과·한계를 같은 수치로 공개한다.

### 5.4 계산 규칙 (FR-10·12·13·14)

- **시청 단위.** 영화 1편 또는 드라마 시즌 1개(watch_unit). 시청량은 편수가 아니라 시간(분)으로 센다(같은 12부작이라도 회당 60분과 24분은 다르다).
- **필요 시간.** 영화는 러닝타임, 시즌은 방영된 회차 러닝타임의 합. 비어 있으면 영화 120분, 회차 45분(애니메이션 장르 24분)으로 추정하고 "추정" 표시. 기본값은 수집 데이터 중앙값으로 보정한다(11절 25번).
- **월 시청 가능 시간.** 프리셋 가볍게 8시간 / 보통 15시간 / 많이 30시간(LIGHT / NORMAL / HEAVY), "주 N회 × 회당 M시간" 환산, 직접 입력(CUSTOM). "가볍게"는 국내 OTT 앱 월평균 이용시간 약 7~9시간(와이즈앱·리테일, 2023~2024년 8월, 스마트폰 기준이라 TV 시청 제외)에 맞췄다.
- **긴 시즌.** 한 달 시간보다 긴 시즌은 같은 서비스를 연속 구독하는 달에 나눠 볼 수 있고 다 본 달에 점수를 얻는다. 연속 구독이 아니면 나눠 볼 수 없다.
- **목적함수.** ① "꼭" 작품 완주 수 최대화 → ② 나머지 우선순위 점수 합 최대화(보고 싶음 2, 여유될 때 1) → ③ 총비용 최소화. 제약은 월 예산과 월 시청 가능 시간.
- **구독 상태 반영.** 무료 이용은 비용 0인 상시 커버, 구독 중은 이번 달 비용 0이고 다음 달부터 유지·해지를 계산한다. 번들은 하나의 가상 서비스. "모름"은 커버로 세지 않는다.
- **배정 규칙(고정).** 우선순위 높은 순 → 필요 시간 짧은 순으로, 볼 수 있는 가장 이른 달부터 채운다.
- **정확해와 그리디.** 정확해는 달마다 예산 안에 드는 서비스 조합을 3개월에 걸쳐 완전탐색하고, 같은 비용에 커버가 더 적은 지배 조합은 미리 제거한다. 즉 "고정된 배정 규칙 아래에서 최선의 구독 조합"이다. 그리디는 달마다 목적함수 증가가 가장 큰 조합을 차례로 고른다. 운영 경로는 정확해 기본, 후보 조합 수가 상한을 넘으면 그리디(TECH T-4, 상한은 11절 30번).
- **롤링.** 이번 달만 확정, 다음 두 달은 예상. 매월 데이터 갱신 후 재계산해 카탈로그 변동을 반영한다.
- **결제일과 해지.** 구독은 월 단위로 계산하고(일할 없음) 결제일 기본값은 매월 1일이다. 해지를 예약해도 결제 기간 끝까지 이용할 수 있다고 보고, 가입 시점에 "가입 즉시 해지 예약 권장"을 안내한다(서비스별 정책은 11절 27번).
- **남은 작품의 이유 코드.** 판정 순서 NO_PROVIDER → UNKNOWN → BUDGET → TIME으로 첫 번째로 맞는 것을 쓴다. NO_PROVIDER(7개 서비스에 없음: 7개 모두 "없음"), UNKNOWN(제공처 정보 없음: "있음"은 없고 "모름"이 있음), BUDGET(예산 부족), TIME(시청 시간 초과). BUDGET·TIME의 세부 판정은 TECH 1절.

**플랜 상태.** 계산과 저장을 분리한다(11절 7번).

| 상태 | 뜻 | 규칙 |
|---|---|---|
| DRAFT | 계산했지만 저장하지 않은 플랜 | 사용자당 1개. 새로 계산하면 기존 DRAFT와 딸린 월별 상품·작품 배정 행을 지우고 덮어쓴다. 알림·재계산 대상 아님 |
| ACTIVE | 저장한 현재 플랜 | 사용자당 1개. 알림과 매월 재계산의 기준 |
| ARCHIVED | 새 플랜으로 물러난 이전 플랜 | 변경 내역에 사용 |

저장 시 DRAFT의 data_as_of가 최신 수집 완료 시각보다 이르면 409(`PLAN_DRAFT_STALE`)로 막는다. 수집이 매일 돌면 대부분의 DRAFT가 다음 날 막히므로, MVP에서는 프론트가 409를 받으면 자동으로 재계산해 새 결과를 보여준다. 판정 기준을 좁히는 개선은 TECH T-9(2단계 후보)다.

### 5.5 수집 범위와 갱신 주기 (FR-18 보충)

- 7개 서비스 중 한 곳이라도 한국에서 구독으로 제공하는 후보 작품만 미리 수집한다. TMDB 전체 카탈로그는 복제하지 않는다.
- discover는 후보 수집에만 쓰고, 상태는 작품·시즌별 제공처 조회로 확정한다. 시즌 0(스페셜)은 수집하지 않는다(ERD).
- 사용자가 찾는 작품이 DB에 없으면 TMDB 검색으로 단건 수집해 저장한다(FR-01).
- 갱신은 찜에 들어 있는 작품(refresh_tier = DAILY) 매일, 나머지 후보(WEEKLY) 주 1회. MVP는 일괄 갱신, 계층 분리는 2단계 O3.
- TMDB 호출은 초당 약 40회 한도 아래로 제한하고 429 응답 시 백오프한다.

### 5.6 서비스 표현 원칙

모든 화면과 메일에 적용한다.

- 제공 여부·추천·독점은 "확정"이 아니라 **"확인된 범위"**로 쓴다.
- 데이터는 하루 단위 갱신이고 최대 수 시간 지연될 수 있으므로 **데이터 기준일**을 함께 보여준다.
- 확실하지 않은 데이터는 **"모름"**으로 표시한다.
- 쿠팡플레이는 **"데이터 부족"** 서비스로 표시한다(data_quality = INSUFFICIENT).

## 8. 데이터 요구사항

### 8.1 핵심 엔티티

스키마·상태값·삭제 정책은 [ERD.md](./ERD.md)가 기준이다(서비스 테이블 24개).

| 영역 | 엔티티 | 의미 |

| A 작품·데이터 | ott_service, tmdb_provider, title, watch_unit, availability, availability_change (+ genre, title_genre, title_cast) | 7개 서비스, 제공처 매핑, 작품, 시청 단위, 제공 상태와 변경 이력 |
| B 상품·요금 | subscription_product, product_component, product_price | 단품·번들을 "구독 상품"으로 통일, 적용 시작일 있는 가격 이력 |
| C 사용자 | users, user_setting, user_subscription, user_price_override, wishlist_item | 계정, 예산·시청 시간·알림 설정, 구독 상태, 금액 수정, 찜 |
| D 플랜 | plan, plan_month, plan_month_product, plan_item, plan_assignment, calc_run | 플랜 스냅샷, 월별 상품·배정, 알고리즘 비교 기록 |
| E 알림·운영 | notification_outbox (+ BATCH_*, shedlock) | 알림 대기·발송 이력, 수집 실행 이력 |

Refresh Token, 요청 제한 버킷, 캐시(작품 상세, 독점 목록, 계산 결과)는 Redis에 둔다. 독점 목록은 별도 테이블 없이 availability에서 계산한다.

### 8.2 데이터 근거 (소스와 정확도)

**소스 선택.** TMDB로 확정했다. 국내 OTT는 공개 카탈로그 API가 없고, TMDB는 JustWatch 기반 제공처 데이터를 공식 API로 주며 KR의 7개 서비스를 모두 다룬다(쿠팡플레이는 TV만, 영화 없음). Watchmode는 한국 로컬 드라마 데이터가 비어 보조 검토에 그쳤고, Movie of the Night는 한국에서 해외 서비스만 지원해 제외했다.

**검증 방법.** 서비스당 5건(총 35건)을 무작위로 뽑아 TMDB가 "구독 제공"이라고 한 작품을 실제 앱에서 확인했다(정밀도). 재현율(앱에 있는데 TMDB에 빠진 작품)은 측정하지 않았다. 결과: 유효 33건 중 30건 일치(약 91%, 중복을 뺀 고유 작품 31건 중 28건). 왓챠 편차가 크고 표본이 작아 서비스별 수치로 본다.

| 넷플릭스 | 5/5 | 제목 검색에 안 잡혔지만 실제 존재한 작품 1건 포함 |

**발견한 문제와 설계 변경.** discover 조회는 "해당 서비스가 제공"과 "어느 서비스든 구독 제공"을 따로 만족해도 통과시켜, 웨이브 샘플 2건(웨이브는 구매만, 구독은 다른 서비스)이 잘못 들어왔다. 그래서 가용 여부는 작품별 제공처 조회의 flatrate에 그 서비스가 직접 있는지로만 판정하고 discover는 후보 수집에만 쓴다.

- 서비스당 3~5건 수동 확인이고 인기순 상위에서 뽑아 마이너 작품 정확도는 모른다.
- 불일치 3건이 모두 왓챠의 오래된 영화라 계약 만료 반영 지연이 원인이라는 가설이 있으나 입증되지 않았다.

- 재현율 미측정이라 독점 목록은 다른 서비스 쪽 누락으로 잘못 표시될 수 있다("확인된 범위" 표현).

## 9. 개발 단계

**진행 원칙.** ① 프론트 골격 우선: 1주차에 전체 화면을 목업(MSW)으로 만들어 흐름을 확정하고 OpenAPI 초안을 도출한 뒤 API가 완성되는 대로 교체한다. ② 위험한 작업은 일찍: 순수 Java 계산 엔진은 1주차에 골격과 동시에 착수하고, 배포 경로(Vercel → /api 프록시 → Cloudtype)도 1주차에 얇게 확인한다. ③ 각 단계는 배포까지 끝나야 완료다. 주차는 예상치다. 작업 구분: H 직접 하는 비개발 작업, B 백엔드(직접 작성), F 프론트(AI 작성, 흐름·디자인·인증 코드는 직접 검토).

**직접 판단 지점.** F1 이후 목업을 직접 눌러 보고 흐름을 승인해야 OpenAPI 초안이 고정된다. H3가 늦으면 F2 이후 화면을 다시 손봐야 한다. F4의 토큰 처리 코드는 직접 검토한다.

**UI 선행 순서.** 화면에서 필요한 데이터를 먼저 추리고 그 뒤에 API와 DB를 확정한다.
- MVP: 전체 화면 목업(F1) → 목업 승인과 화면 관련 결정(11절 14·18·19·20번) → OpenAPI 초안 → ERD 보정과 사용자·플랜·알림 영역(C·D·E) DB 마이그레이션 확정 순서다. 작품·상품 영역은 승인 뒤에 만든다.
- 2단계 이후: 기능마다 화면 목업 → 계약(`openapi.yaml`)에 API 추가 → 백엔드 구현 → 목업을 실제 API로 교체 순서로 한다. `openapi.yaml`은 CI에서 구현과 대조하므로 아직 구현하지 않은 API에는 `x-planned: true`(이름은 제안)를 달아 대조에서 제외하고, 구현이 끝나면 표시를 지운다. 계약 초안을 별도 파일로 나누지 않는다.

**MVP 완료 기준.** ① 로그인한 사용자가 구독 상태와 예산·시청 시간을 입력하고 작품을 검색해 찜한 뒤 3개월 플랜을 계산해 저장할 수 있다. ② 비로그인 방문자는 검색과 작품 상세를 볼 수 있다. ③ 계산 엔진이 정답 테스트를 통과하고 정확해·그리디 비교를 한 번 이상 기록한다. ④ 배포 환경에서 로그인과 계산이 동작한다.

**MVP에서 미루는 것.** 알림 메일, 매월 재계산, 번들과 광고형 요금제, 독점 목록, 탈퇴, 관측 도구, LLM. MVP의 저장 플랜은 사용자가 직접 재계산해 갱신한다.

## 10. 제약·가정·리스크

**제약.** 기간 약 2개월, 저예산 운영(절약할수록 좋음). 백엔드는 Cloudtype, DB는 Supabase(PostgreSQL), Redis는 Redis Cloud, 프론트는 Vercel에서 무료 티어로 시작한다.

**가정** (틀리면 요구사항이 바뀐다)
- 구독은 월 단위로 계산하고(일할 없음) 결제일 기본값은 1일이다.
- 월 구독은 해지를 예약해도 결제 기간 끝까지 이용할 수 있다(11절 27번).
- 계획 기간 3개월 동안 카탈로그가 유지된다고 보고, 매월 재계산으로 보정한다.
- 요금제·번들 가격은 운영자가 직접 입력하고, 실제 지불 금액이 다르면 사용자가 수정한다.
- 사용자는 한국에서 쓰고 KR 지역 제공처 데이터를 쓴다.
- 한 사용자의 찜은 수백 개 이하다(상한은 11절 30번).
- 러닝타임을 기본값으로 추정해도 계획의 큰 흐름은 바뀌지 않는다.

## 11. 결정 현황

번호는 TECH의 `R11-N`이 참조하므로 바꾸지 않는다. 담당·기한은 정해지지 않았다.

**기획 단계 확정(요약).** 메인 기능을 "찜 전체 최저가 + 12개월 달력"에서 "예산·시청 시간·우선순위 기반 3개월 롤링 플랜"으로 변경 / 시청 단위는 영화 1편 또는 시즌 1개 / "꼭" 최우선 목적함수, 시간 기반 시청량, 예산 필수 / 서브 기능은 로그인 없이 / 프로젝트 이름 OTT내비(ottnavi, 목적지 검색·경로 안내·재탐색을 내비게이션에 빗댐), 모노레포 `ottnavi`(backend, frontend, docs, infra), 패키지 `com.ottnavi`, 도메인 ottnavi.shop(구매 전 갱신 가격 확인).

**확정**

1. [x] 디자인 방향은 작업하면서 정한다(F1~F2 진행 중).
